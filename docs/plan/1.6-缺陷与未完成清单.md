# 二、已核实的功能性缺陷（建议优先修）

## 2.1 ★ EGO 情绪温度无效 —— 整条链路白传

| | |
|---|---|
| **现象** | EGO 按情绪算出的温度，实际从未作用到请求上 |
| **证据** | `bot_core.py:5896` `effective_temperature = AI_TEMPERATURE`，**从不用** `personality_temperature`；而 `personality_temperature` 从 5502 → 5977 → 6314 → 6324 → 6820/6837/6858/8073 一路透传 |
| **影响** | 「情绪影响说话风格」这一功能**实际不存在**。所有调用恒用全局 `AI_TEMPERATURE` |
| **成本** | 低（1 处：让 `effective_temperature` 优先取非空 `personality_temperature`） |
| **风险** | 低。但需确认 EGO 给出的温度范围合理（有插件在算） |

## 2.2 ★ 私聊画像未生效 —— 实参恒为空串

| | |
|---|---|
| **现象** | 私聊注入「用户画像」的功能从未真正启用 |
| **证据** | `bot_core.py:8037` `pm_ctx = ""`（硬编码空串）→ `:8073` 把它传进 `call_deepseek(private_memory_context=pm_ctx)`；消费侧 `:6077` 写好了 `if private_memory_context:` 分支，但永远是假 |
| **影响** | 私聊时 AI 拿不到对方画像 |
| **成本** | 低（接上真正的画像来源）。**但需先确认画像数据源在哪、格式如何** —— 这点**未确认** |
| **风险** | 中：需先查清数据源，别凭空造一个 |

## 2.3 ★ 群聊没有白名单 —— Bot 进任何群都会说话

| | |
|---|---|
| **现象** | 只要适配器转发了群消息，Bot 就会参与回复；没有「只在这些群工作」的开关 |
| **证据** | 群分支只查 `_group_restriction(gid,"reply_enabled",True)`（`bot_core.py:7467 / 7487`），**默认 True**；无限定群号集合 |
| **影响** | 被拉进陌生群会立即开始回复 —— 用户明确不想要的行为 |
| **成本** | 低（加 `group_whitelist` 配置 + 一处判定） |
| **风险** | 低。但要定清语义：**白名单为空 = 全部允许（兼容现状）还是全部禁止？** 需用户拍板 |

## 2.4 ★ `bTrigger` 保存路径没有空值守卫 —— 点保存必抛 TypeError

| | |
|---|---|
| **现象** | behavior 页点「保存」会抛异常 |
| **证据** | JS 引用 `bTriggerWords / bTriggerSave / bTriggerTextAt / bTriggerQuote / bTriggerBotNick`，但 DOM 里 **5 个 id 全部 0 定义**（实测 `grep -c 'id="bTriggerWords"'` = 0，其余同）；手册 §8.5(3) 指出保存路径 `L2749–L2755` 无空值守卫 |
| **影响** | 一个页面功能直接坏掉，且报错只在 console |
| **成本** | 低（补守卫）或中（补齐 DOM） |
| **风险** | 低。**但手册明令「不要顺手修好」** —— 属功能变更，需你确认要哪种修法 |

## 2.5 ★ `dashCards` 容器不存在 —— 仪表盘数值静默不更新

| | |
|---|---|
| **现象** | 仪表盘上的数字不刷新，且**不报错** |
| **证据** | `qsa('#dashCards .card')` 的容器在 DOM 中不存在（实测 `grep -c 'id="dashCards"'` = 0） |
| **影响** | 仪表盘看起来「在工作」，实则数据不动 |
| **成本** | 低 |
| **风险** | 低。同属「不要顺手修」范畴，需你确认 |

## 2.6 其余 4 个「被 JS 引用但 DOM 不存在」的 id

| id | 后果 |
|---|---|
| `decodeGrid` | 启动页字符雨从未运行 |
| `galleryGrid` | 图库网格无容器 |
| `memoryDecodeAll` / `memoryEncodeAll` | 记忆页「全部解码/编码」按钮无效 |

**证据**：逐个 `grep -c 'id="…"'` 均为 0。**影响**：对应动效/按钮静默失效。**成本**：低（但要先确认原始设计意图）。

# 三、已核实的可靠性 / 稳定性缺陷

## 3.1 多个锁声明了但从未使用 + 一处真竞态

| | |
|---|---|
| **证据** | `_group_meta_lock`(476) / `_replies_lock`(479) / `_meme_lock`(481) 声明后**从未 `with` 使用**；`_buffer_lock`(478) **只在 4960 用了一次**，而缓冲写入与 Timer 线程 `pop` **都不加锁** |
| **影响** | 「看起来做了并发保护，其实没有」。Timer 线程与主线程同时动 `GROUP_MSG_BUFFER` 存在竞态 |
| **成本** | 中（要逐个判断该不该加锁，不能无脑加） |
| **风险** | 中：加锁位置错了会引入死锁 |

## 3.2 `save_state` 吞掉所有异常

| | |
|---|---|
| **证据** | `bot_core.py:2174-2180`：`try: data_store.write_json(...)` / `except: pass` |
| **影响** | 状态写盘失败**无声无息**，重启后状态莫名其妙丢失 |
| **成本** | 低（`except Exception as e:` + 记日志） |
| **风险** | 极低 |

## 3.3 端口顺延 → Electron 窗口永远出不来

| | |
|---|---|
| **证据** | `webui_server.py:4101-4103` 在 8080 被占用时顺延并写 `last_port.txt`；`main.js:169/173/306` 把 URL **写死** `localhost:8080`，从不读该文件 |
| **影响** | 一旦顺延，窗口按 `did-fail-load` 每 2 秒重试 8080 **永远白屏**，而后端其实正常 |
| **成本** | 低（main.js 读 `last_port.txt`） |
| **风险** | 低 |

## 3.4 `web_operator` 的 Playwright 浏览器缺失

| | |
|---|---|
| **证据** | 包内 Python 的 Playwright 是 1.63 → 需 `chromium-1243`；机器上只有 `chromium-1228`（属系统 Python 的 1.62） |
| **影响** | 任何网页自动化都报 `Executable doesn't exist` |
| **成本** | 补下载 400+ MB（手册建议「用时再下」） |
| **风险** | 低 |

# 四、已核实的安全加固项

> **注意**：手册已如实标注影响面，**不要夸大**。

## 4.1 `/memes/*` 缺路径校验

| | |
|---|---|
| **现象** | 静态分支（`webui_server.py:1433`）判定失败后**不 `return`**，控制流落到 `/memes/` 分支（2390）；`_serve_meme`（1148）用的是**裸的** `meme_dir / rel` |
| **实测确认** | 静态分支只在 `in_dir and is_file and suffix in _STATIC_EXTS` 时 `return`（1441-1457）；不满足则继续往下 → 2390 分支取 `rel = path[len('/memes/'):]` → 上溯可读出 meme 目录之外的文件 |
| **可达性** | 响应**不带 ACAO** + 有 Host 校验挡 DNS rebinding → **属加固缺陷，不是远程可利用漏洞** |
| **成本** | 低（静态分支判定失败即 `return 404`；`_serve_meme` 加 `resolve()` + 前缀校验） |

## 4.2 `GET /api/plugins/action` 的 CSRF 面

| | |
|---|---|
| **证据** | 该端点在 `do_GET`（**1591**）与 `do_POST`（**3491**）**都被处理**，GET 侧参数从 query 取；而 Origin 闸门只加在 `do_POST` |
| **影响** | GET 路径绕过了 CSRF 防护 |
| **成本** | 低（GET 侧也加同样闸门，或直接禁掉 GET 侧） |

# 八、关于「前端先做」的决策依据

手册把 T8 排在最后，理由是「harness 会新增工具调用 / 预算 / 会话日志 / 任务面板等界面元素，现在按旧信息重做完，harness 一上来还得再改一遍」。

**这个理由现在已基本失效**，实测如下：

| 判断 | 证据 |
|---|---|
| harness 侧的界面元素**已经落地** | Agent 页（`515f1c1`）已含对话 / 轨迹 / 本体记忆三块 |
| T7 剩下的 15 项**约九成是后端** | prompt 段注册表、三档拦截语义、权限目录、压缩事务化、委派、上下文锚点 —— 均无新界面 |
| 两套组件方言**已经并存** | 见 5.2：每加一页，不一致加深一层 |
| 二者**无技术依赖** | DOM 契约是冻结的；T7 是后端改动 → 前后做都不冲突 |

**结论**：T7 与 T8 **互不阻塞**，先后纯属优先级选择。若目标是「后面统一」，**前端先做是对的**。

**但必须如实说明代价**：前端重做是全项目**最大且风险最高**的单项任务（248 id / 43 class / 49 data-* 是冻结契约，11 个迁移陷阱），
且**不增加任何能力**。若优先级是「让 agent 真正好用」，T7 的每小时产出更高。

**建议的落地结构（若决定前端先做）**：

| 步骤 | 内容 | 风险 |
|---|---|---|
| **8.0** | 把设计系统令牌**以别名方式**加进 `:root`（`--gold` → `--accent` 等**保留旧名**，因 110 处 JS 依赖），补齐间距/字号刻度。**不碰任何页面** | **零** —— 立刻有统一点 |
| **8.1** | 收敛 5.2 的两套方言（`.ag-*` 与 `.card/.panel` 合一） | 低 |
| **8.2** | 先做 `settings` / `tokens`（含 §8.5 的两个高危陷阱：50 处 `.style.display`、下标取值） | 中 —— 坏了会写错配置 |
| **8.3** | 按重量迁移：`protocol` → `groupmanage` → `memes` → `imagegen` → `behavior` → `bot` → `chatlogs` → `dashboard` → `monitor` → `console` → `memory` → `commands` → `plugins` | 中 |
| 纪律 | **JS 逻辑一行不改**；只动 `<style>` 与模板 class/层级；每页一次 commit + 跑该页交互清单 + **实际观察轮询是否还在刷新** | — |
