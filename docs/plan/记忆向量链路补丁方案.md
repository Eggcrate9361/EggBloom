# 记忆向量链路补丁方案（P0/P1）

> 依据：`docs/zhinao-embedding-eval.md` 的实测结论。向量模型**不换**（Zhinao 在本任务上更差），
> 改为修几处既有缺陷。全部改动不改变对外行为契约，只改"嵌什么"和"嵌几次"。
> 目标：召回 Top-1 0.833 → 0.867、Top-3 0.900 → 0.967（**在 LiGGUF 引擎上实测**），
> embedding 调用量减半，换模型/换引擎时不再静默丢记忆。

|---|---|---|---|---|

## 二、P0-1：带类别前缀嵌入

### 现状

`plugins/ego/super_memory/__init__.py:745-748`（facts）与 `:901-904`（events）都是：

```python
emb = ""
try:
    if _embedder.embed(content):
        emb = json.dumps(_embedder.embed(content))
except Exception:
    pass
```

嵌的是裸 `content`（如 `不喜欢：香菜`），而**读侧展示**是 `f"[{row[0]}] {row[1]}"`（`:1007` / `:1024`），
即 `[偏好] 不喜欢：香菜`。写读两侧的文本形态不一致。

### 改法

嵌 `f"[{category}] {content}"`，与读侧完全对齐。

```python
emb = ""
try:
    _v = _embedder.embed(f"[{category}] {content}")   # 与读侧展示形态一致
    if _v:
        emb = json.dumps(_v)
except Exception:
    pass
```

events 同理：`f"[事件] {event['summary']}"`。

### 依据

同一 30 条查询 × 40 条候选、同一模型，仅切换池文本是否带 `[类别] ` 前缀。
**两个引擎分别测过，方向一致：**

| 引擎 | 口径 | Top-1 | Top-3 | MRR |
|---|---|---|---|---|
| **LiGGUF（插件首选）** | 裸文本 | 0.833 | 0.900 | 0.878 |
| **LiGGUF** | **带前缀** | **0.867** | **0.967** | **0.918** |
| llama-server（兜底） | 裸文本 | 0.833 | 0.933 | 0.885 |
| llama-server | 带前缀 | 0.867 | 0.967 | 0.920 |

两个引擎都是 **+1 条 Top-1**；Top-3 在 LiGGUF 上 +2 条（27/30 → 29/30），llama-server 上 +1 条。
绝对增益不大（30 条样本，1 条 = 3.3 pt），但**成本是 2 行、方向为正、引擎无关**。

类别前缀天然提供了"这是身份/偏好/事件"的类型信号，对 `我念高几了 → [身份] 高三学生`
这类需要类型推断的查询有帮助；且它让**写侧与读侧文本形态一致**（读侧展示本来就带前缀，`:1007` / `:1024`）。

### 影响面

- 只影响**新写入**的 facts/events；
- 不影响 dedup（`WHERE ... content=?` 用的是裸 content，不变）；
- 不影响展示（读侧本来就加前缀）；
- **存量向量会与新向量口径不一致** → 由 P0-3 处理。

## 三、P0-2：去掉重复 embed

### 现状

```python
if _embedder.embed(content):          # 第 1 次
    emb = json.dumps(_embedder.embed(content))   # 第 2 次
```

条件判断和取值各嵌一次，**每条内容嵌两遍**。

在 LiGGUF 引擎上这不是"可忽略的浪费"：单条 **67 ms**（llama-server 只要 5.9 ms），
一条事实入库白烧 **70 ms**，且是在 `after_reply` 的热路径上。群里连着来几条消息时，
这段延迟会直接顶到回复节奏上。**这是本方案里唯一在延迟层面能被立刻感觉到的一条。**

### 改法

缓存到局部变量（见 P0-1 的 diff，两条合并为同一处改动）。

### 注意

`_embedder.embed()` 失败返回 `None`，原写法靠"第一次调用的真值"做判断；改成局部变量后语义等价，
且避免了两次调用之间状态漂移（例如 `_fail_count` 越过 5 导致第二次返回 None，原写法会写进 `"null"`）。

> 顺带修掉一个隐性 bug：原写法在"第一次成功、第二次失败"时会执行 `json.dumps(None)` → 存进字符串 `"null"`，
> 读侧 `json.loads("null")` 得到 `None`，`_vec_sim` 返回 0.0 —— 这条记忆从此永远召回不到。

## 四、P0-3：存量向量重算

### 为什么必须做

P0-1 改变了嵌入文本形态。新旧向量混存时：

- 查询向量是裸用户消息，与两种文档向量的偏移不同；
- 排序会出现不可解释的抖动（同一批记忆，有的按新口径、有的按旧口径打分）。

现在库里只有 `facts` 7 条（其中 3 条有向量）、`events` 1 条，重算成本接近 0；但**必须在 P0-1 上线的同一次
发版里做完**，否则越拖越贵。

### 实现

在 `plugins/ego/super_memory/__init__.py` 增加：

```python
def reembed_all(self, scope_id: str = "", dry_run: bool = False) -> Dict[str, Any]:
    """按当前口径重算 facts/events 的向量。幂等，可重复执行。

    只重算 embedding / embed_sig，不动 content / confidence / tier。
    scope_id 为空时处理全库。
    """
    stat = {"facts": 0, "events": 0, "failed": 0}
    try:
        conn = sqlite3.connect(DB_PATH)
        where, args = ("WHERE scope_id=?", (str(scope_id),)) if scope_id else ("", ())

        for table, select_sql, build in (
            ("facts",  f"SELECT id, category, content FROM facts {where}",
             lambda r: f"[{r[1]}] {r[2]}"),
            ("events", f"SELECT id, summary FROM events {where}",
             lambda r: f"[事件] {r[1]}"),
        ):
            for row in conn.execute(select_sql, args).fetchall():
                v = _embedder.embed(build(row))          # 与写入路径同一口径
                if not v:
                    stat["failed"] += 1
                    continue
                if not dry_run:
                    conn.execute(
                        f"UPDATE {table} SET embedding=?, embed_sig=? WHERE id=?",
                        (json.dumps(v), _embed_sig(v), row[0]))
                stat[table] += 1

        if not dry_run:
            conn.commit()
        conn.close()
    except Exception as e:
        return {"ok": False, "error": str(e), **stat}
    return {"ok": True, "dry_run": dry_run, **stat}
```

`stat` 的键名与表名对齐（`facts` / `events`），面板直接显示。`_embed_sig` 定义见第六节（P1-2）；
若决定跳过 P1-2，把 `embed_sig=?` 那半句去掉即可。

在 `plugins/super_memory/__init__.py` 的 `PLUGIN_ACTIONS` 里挂一个动作：

```python
"reembed_all": lambda params: _memory.reembed_all(
    scope_id=str((params or {}).get("scope_id") or ""),
    dry_run=bool((params or {}).get("dry_run")),
),
```

### 执行顺序

1. 停 bot（避免写入竞争）；
2. 备份：`copy plugins/ego/super_memory/data/super_memory.db  super_memory.db.bak-YYYYMMDD`；
3. `reembed_all(dry_run=True)` 看计数是否符合预期（现在应为 facts 7 / events 1）；
4. `reembed_all()` 实跑；
5. 起 bot，抽查 `recall` 返回的 `sim` 是否落在新分布（期望 0.4~0.8，而不是旧口径的 0.5~0.9）。

### 回滚

DB 是单文件，直接回滚 `.bak` 即可。

**只回滚代码、不回滚数据是不安全的**：新向量按带前缀口径算，旧代码按裸文本召回，维度一样（都是 512），
P1-1 抓不到，表现为召回质量悄悄降一点点。要回滚就**代码和 `.bak` 一起回**。

## 五、P1-1：维度不一致不再静默归零

### 现状

`plugins/ego/super_memory/__init__.py:220-222`：

```python
def _vec_sim(a, b):
    if not a or not b or len(a) != len(b):
        return 0.0
```

换模型（512 → 768）时，**所有存量向量直接算 0 分**，再被 `sim_floor` 筛掉 —— 表现为"记忆突然全忘了"，
但日志里一个字都没有。

### 改法

保留 `0.0` 的返回值（不改变行为），但加一次性告警，并把维度不一致的条数暴露出来：

```python
_DIM_MISMATCH = {"count": 0, "pairs": set()}

def _vec_sim(a, b):
    """余弦相似度，a/b 为等长 float 列表。维度不一致时归零并计数（不静默）。"""
    if not a or not b:
        return 0.0
    if len(a) != len(b):
        _DIM_MISMATCH["count"] += 1
        key = (len(a), len(b))
        if key not in _DIM_MISMATCH["pairs"]:
            _DIM_MISMATCH["pairs"].add(key)
            print(f"[SuperMemory] 向量维度不一致 {len(a)} vs {len(b)}："
                  f"极可能是换过 embedding 模型，需执行 reembed_all()")
        return 0.0
    ...
```

`get_vector_stats()`（`:1415`，UI 已经靠它标"未向量化"条数）里加上：

```python
"dim_mismatch": _DIM_MISMATCH["count"],
"dim_seen": sorted(list(_DIM_MISMATCH["pairs"])),
```

## 六、P1-2：向量模型标识（可选，建议做）

### 问题

`facts` / `events` 的 `embedding` 列是裸 JSON 文本，**不知道自己是谁算的**。换模型时无法区分，
只能全量重算；而全量重算在库变大后是分钟级。

### 改法

加一列 `embed_sig TEXT`，写入时打标：

```sql
ALTER TABLE facts  ADD COLUMN embed_sig TEXT DEFAULT '';
ALTER TABLE events ADD COLUMN embed_sig TEXT DEFAULT '';
```

签名取"引擎 + 模型名 + 维度"——三者任意一个变化，向量就不在同一个空间：

```python
def _embed_sig(vec) -> str:
    eng = "ligguf" if _embedder._init_dll() else "http"
    return f"{eng}:{_embedder.model or 'unknown'}:{len(vec) if vec else 0}"
```

带上引擎是必须的：DLL 加载失败会静默降级到 HTTP，两者同文余弦只有 **0.891**（不是 1.0），
混在一个库里会让排序莫名抖动，而 `dll_path` 为空、文件被杀软删掉、路径含中文导致加载失败
—— 这些都会触发降级且**不留痕迹**。`ligguf:512` 与 `http:512` 一眼就能分开。

写入时一并落库；召回时若 `embed_sig` 与当前签名不符，只降权不全丢（与 P1-1 配合）：

```python
cross = (row_sig and row_sig != _current_sig)
score = sim * (0.8 if cross else 1.0)     # 跨口径的旧向量降权，而不是直接 0
```

这样即便忘了跑 `reembed_all`，也不会一夜之间"失忆"，而是平滑退化。

> 这一条改表结构，需走既有的 `_init_db()` 迁移套路（仓库里已有 `ALTER TABLE ... ADD COLUMN` 的
> try/except 先例，见 `:580-600`）。

## 七、验证

### 7.1 先确认当前跑的是哪条引擎

这一步不能跳。两条路径的向量**不在同一个空间**（同文余弦 0.891），混着用等于混口径：

```powershell
python -c "from plugins.ego.super_memory import _embedder as e; \
  print('DLL 生效:', e._init_dll()); print('dll =', e.dll_path); print('url =', e.url)"
```

- `True` → 走 LiGGUF（单条 ~67 ms，512 维）；
- `False` → 静默降级到 `embed_url` 的 llama-server（单条 ~6 ms，口径不同）。

**本机实际情况（已查证）**：部署目录
`<EggBloom_v3>\models\` 里有
`ligguf_embed.dll`（298,496 B）+ `bge-small-zh-v1.5-f16.gguf`（47,886,240 B），
与 `<LiGGUF 源码目录>\ligguf_embed.dll`、以及本次评测用的 `bge.gguf` **同尺寸同文件**。
这个目录是 `_EMBED_ASCII_CACHE`（`:173`）—— 中文路径被 `_ascii_mirror` 镜像过来的结果，
说明**运行态确实走 LiGGUF**。所以第二节那两组 LiGGUF 数据是在真实 DLL + 真实模型上跑的，不是代理指标。

反过来说：源码树 `<仓库根>` 是纯 ASCII 路径，不走镜像，而 `bot_config.json:247` 的 `embed_dll` 是空串，
`_init_dll()` 会失败 → **在仓库里跑测试看到的是 HTTP 口径**。跑基准前先确认，否则数对不上。

把 `probes2.json` 的池文本换成从真实库导出（`SELECT category, content FROM facts`），用**实际引擎**跑，
确认 Top-1 ≥ 0.867、Top-3 ≥ 0.967。低于这条线说明前缀没生效、或被别的东西盖掉。

## 九、不做什么（避免范围蔓延）

- **不动 `embed_min_sim=0.35`**：实测该阈值对 bge 标定准确（真匹配 100% 保留、干扰项放行 29%），
  前缀改动后分布会略上移，但没有证据要求调整。要调等端到端基准出数再谈。
- **不动 `-c 8192`**：LiGGUF 根本不经过 llama-server，这条只在 HTTP 兜底时才生效。
  而且两个引擎的**溢出行为不同**：LiGGUF 里 `bert_embed()` 是 `toks.resize(n_context - 2)` —— **静默截断**到 510；
  llama-server 则直接 **HTTP 500**（实测 1935 字中文、4000 字符英文均报错），`embed()` 返回 `None`，那条记忆干脆没有向量。
  当前数据够不着这个边界（facts ≤20 字、事件摘要 `[:300]` ≈ 290 token），属于"已知但暂时不吃亏"。
  真要动，该改的是 `text[:800]` 的口径（按 token 截而不是按字符），不是 `-c`。
- **不混引擎**：DLL 与 HTTP 的向量不在同一空间（同文余弦 0.891）。某台机器 DLL 加载失败会**静默降级**到 HTTP，
  新旧向量就此混在一个库里且无任何标记。这是 P1-2 要根治的事（`embed_sig` 带引擎名），
  在此之前至少先做 7.1 的引擎确认。
- **不给 `messages` 加向量**：那是 P1 独立工单（覆盖率问题），与本补丁正交，混在一起会让回归不可归因。

### 一处与方案不符（以实测为准）

### 还没做：生产库重算

**备份已做**：`plugins/ego/super_memory/data/super_memory.db.bak-20261103-preembed`
（1,040,384 B，与源库 SHA256 一致）。

**重算没做，是故意的** —— 方案自己写明"必须在 P0-1 上线的**同一次发版**里做完"。
当前 `resources\app` 跑的还是补丁前的代码（写裸文本向量），此刻重算会让库里一半新口径、

1. 把 `plugins/ego/super_memory/__init__.py` 与 `plugins/super_memory/__init__.py`

2. 重启整个 app（改了 Python 就要重启，见交接 §5.3）；
3. `POST /api/plugins/action` → `{"plugin":"super_memory","action":"reembed_all","params":{"dry_run":true}}`
   看计数是否 `facts 6 / events 60 / failed 0`；
