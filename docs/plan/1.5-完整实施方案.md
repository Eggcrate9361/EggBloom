## 〇、先说清楚动作数量（我在这个问题上错过两次，这次有完整证据链）

**最终结论：驱动提供 190 个动作，EggBloom 调用了其中 25 个（13.2%），165 个从未使用。**

证据链：
1. **190** 来自 SnowLuma **官方注册表** `ACTION_GROUPS`（源文件第 11855–11904 行）的分类合计：
   信息 5 + 消息 5 + 好友 3 + 群信息 6 + **群管理 17** + 群文件 12 + 请求 2 + **扩展 113** + 群相册 8 + **空间 9** + 系统表情 4 + 流式接口 6 = **190**
2. 它由**四种 wrapper**定义，这也是我第一次数错的原因：

| wrapper | 数量 | 说明 |
|---|---|---|
| `defineAction` 直接定义 | 125 | 我的正则只抓到了这一类 |
| `groupAction` | 53 | **会注入 `group_id`** —— `send_group_msg`/`set_group_ban` 都在这类里 |
| `groupUserAction` | 7 | 注入 `group_id` + `user_id` |
| `defineStreamAction` | 5 | 流式接口 |

**我第一次数成 184（宽松正则，噪声混入）；第二次数成 128/仅 `defineAction`，把 60 个 wrapper 动作全漏了，于是把"已用"误算成 14。**

3. **25 个已用**是拿 190 全量清单在 EggBloom 全部 `.py` 源码里做字面量匹配得出的，列表完全合理。

### 调用约定（已从源头确认）

> **动作名就是 HTTP 端点名。** `action = url.pathname 去掉配置的 path 前缀`（`index.mjs:216412-216419`）。
> 本机 `config/onebot.json` 的 httpServer 是 `path:"/"` + `port:3000` → **`POST http://127.0.0.1:3000/<动作名>`**。
> 别名同样可用；也支持根路径 + body `{action, params, echo}`、GET 查询串、表单；仅 GET/POST。
> 响应结构：`{status, retcode, data, message, wording, echo}`。

**这意味着 EggBloom 的 `ctx.api_call(action, params)` 直接就能调这 190 个动作中的任何一个**（ABI v2 已就绪），**无需任何底层开发**。

### 2.1 ⚠️ 两处必须先知道的硬事实

1. **`delete_group_album_media` 不存在** —— 源文件（第 8761 行）里叫 **`del_group_album_media`**。
   我上一版方案的 M4 表里就写错了这个名字，照抄会直接调用失败。
2. **群待办三兄弟的 `message_id` 有隐含约束**：必须是**本进程缓存过**的群消息，
   否则调用失败且不会告诉你原因。**先用 `get_group_todo_list` 拿 id**，不要自己拼。

这两条都不是我推断的，是提取方在源文件里逐行确认（并明确标注了"未能确认"的另外 281 项，**没有一处猜测填充**）。

理由：这些能力大多是**偶发使用**，单独建插件会让插件列表膨胀（而"干净"正是你的要求之一）。

## 四、harness 设计稿

### 4.1 先定性：QQ bot 的 harness ≠ 编码 agent 的 harness

我读了 DSH 的真实设计文档（它随包自带中文文档，在 `D:\deepseek\resources\app.asar` 里，283 个包）。
它的 harness 是给**编码 agent** 的：工具是文件/bash/工作区，会话是**单用户任务驱动、有终点**。

EggBloom 完全不同：

| 维度 | 编码 agent（DSH） | QQ bot（EggBloom） |
|---|---|---|
| 驱动 | 用户下达任务 | **外部事件流**（消息永远在来） |
| 会话 | 有终点 | **永不结束** |
| 参与者 | 单用户 | **多人、多群，各自有上下文** |
| 主要决策 | "怎么完成任务" | **"要不要说话 / 说什么 / 要不要动手"** |
| 成本来源 | 长任务上下文 | **高频短交互**，单次便宜但量大 |

**所以能搬的是架构模式，不是工具集。**

### 4.2 从 DSH 提取的可移植模式（我读到的原文机制）

| 模式 | DSH 的做法 | 对 EggBloom 的意义 |
|---|---|---|
| **会话即日志** | 每个"被接纳的事实"append 进 session log；**请求从日志派生**，不是攒在内存变量里 | EggBloom 现在是 `chat_history` 全局 dict + 一堆缓存，改这个能同时解决可观测性与压缩 |
| **工具分「并行安全/独占」** | 并行安全最多 10 个重叠；**独占调用单独跑并构成排序屏障** | EggBloom 的 OneBot 动作天然有这个问题：`send_msg` 可并行，`set_group_ban` 要独占 |
| **工具失败返回结果而非终止** | 普通工具失败返回最终结果，**不中止当前轮次** | |
| **schema 只注册即生效** | `ctx.tools.register(defineTool({...}))`，注册表自动把 schema 送进系统提示词 | 这正是 EggBloom ABI 缺的一块 |
| **压缩：搬结构，不搬数字** | 事务化（标记对）+ 结构化检查点 + **替换而非删除** + 不逐字复制上一版 | EggBloom **完全没有**上下文预算。但**阈值与段名必须按 EggBloom 语料重标**——见 §4.6 |
| **KV Cache 是架构约束** | 提示词变更时若路由支持就**追加到缓存历史之后**，而不是原地改写 | 直接决定成本，且**能用现有的 `cache_hit_rate` 验证** |
| **有界保留原语 + spill** | `ItemRetainer`（持续 drain 得精确省略计数）+ `TextRetainer`（**按字节** head/tail、**在切割处修剪不完整码点**——中文场景关键）；超预算落盘 + 内联首尾预览 + 路径 + 读取提示 | 成本极小的两个纯函数 |
| **三档拦截语义** | `waterfall`（可重排）／`guard`（**单调，拒绝后下游无法推翻**）／`observe`（只读、异常隔离） | EggBloom 有 priority 短路，**缺的正是语义分档** |
| **人类输入的宿主证明** | source 由框架填写，**插件/调度器不能继承人类权限** | EggBloom 只检查 `sender` 字段 —— 多人 + 插件的**防伪造根问题** |
| **spill / output-retention** | 超大输出溢出到磁盘，只留引用 | 日志与工具结果都用得上 |
| **权限分档 + 用户批准** | `permission-presets` / `user-approval`，危险操作分级询问 | EggBloom 的 `group_actions` 目前无分级 |

### 4.4 与 ABI 的关系：**必须先修那个缺口**

`docs/CORE_FLOW.md` 已记录：**typed `on_before_reply` / `on_after_reply` 在 `bot_core` 从未被派发**
（旧式钩子有 5 处，typed 版 0 处）。

harness 必须能往 prompt 注入计划、工具结果、观察 —— **不修这个，harness 无法落地**。
修法已在 CORE_FLOW 写明：在 5 个旧式派发点并列补 typed 派发，**且必须在 `6263` 同一处聚合**（否则两套 skip/inject 会打架）。

### 4.5 建议的实现顺序（按「收益 ÷ 成本」排序，来自调研）

我原先凭直觉排的 H1→H6 顺序**不是最优的**。调研文档给出了 15 项按收益/成本排序的清单，前四项是**高收益低风险**：

| 序 | 项 | 为什么排这个位置 | 成本 |
|---|---|---|---|
| **1** | **策略快照追加（保住前缀缓存）** | 主要是把「模式切换就改写 static_prompt」改成「追加动态段」。**而且能用现成的 `token_stats.py` 的 `cache_hit_rate` 直接验证效果** | 小 |
| **2** | **有界保留原语 + spill 落盘** | 两个纯函数 + 一个落盘目录 + 一个读取入口。**立刻解决"工具输出/日志太长"** | 小 |
| **3** | **事件溯源会话日志**（先只覆盖一个群的对话历史做试点） | 后面多项依赖它 | 中 |
| **4** | **prompt 段注册表 + 严格渲染** | 要改 `ego` 各子插件与 `slang_injector` 的塞入方式 | 中 |
| 5 | 三档拦截语义（waterfall/guard/observe） | `plugin_manager.execute_hook` 已在，主要是加语义档位 | 中 |
| 6–8 | 权限目录 + 审批 seam + **人类输入宿主证明** | 需要「管理员应答者」实现 | 中 |
| 9 | 压缩的事务化 + 结构化检查点 | **依赖第 3 项** | 中 |
| 10–15 | 卸载 fail-closed、逐群能力集、内核/实现分离、后台委派、跨天任务、压力锚点测量 | 都要动核心 | 大 |

**关键调整**：
- 我原方案把"预算压缩"当第一步 —— 它实际排在第 9（依赖会话日志），**先做会返工**
- **ABI 缺口修复**不在这 15 项里，但它是**前置条件**（harness 要注入 prompt 就得先修），建议与第 1、2 项并行
- **前三项都不需要动 `bot_core` 的回复链路**，风险低

### 4.6 ❌ 明确**不要**搬的东西（调研列了 19 项，这里挑最关键的）

| 不要搬 | 原因 |
|---|---|
| **PTC（`run_code` + 生成 SDK）** | 我在上一版方案里把它说成"省 token 的关键"，**那是错的**。QQ bot 调用链只有 1–3 步，function calling 更可靠；且 PTC 的中间值**只存在于执行局部、无法从会话回放重建、可能耗尽内存** —— 对永久在线的 bot 是**稳定性风险**，不是收益 |
| **`mode: native/ptc/both` 这个配置轴** | 没有 PTC 就没有这个轴 |
| **压缩的阈值与段名**（`0.8` / `65536` / 段名 `Files and Code`） | 按「长编码会话、128k+ 窗口、工具输出巨大」标定。**QQ bot 每个群是独立小会话**，照抄会**过度压缩**。只搬结构，数字必须重标 |
| **`goal` 的「agent 空闲就自动续跑」** | **对永久在线、多人共享的 QQ bot 是危险行为** —— 会无人干预地连续行动最多 256 轮。可搬状态机，**必须换掉触发源** |
| **并发默认值**（`maxParallelToolCalls=10`、`maxActiveSubagents=8`、`maxTotalAgents=1000`） | 为"单用户本地编码、要跑满 CPU"标定。QQ bot 的约束来自 **LLM rate limit + QQ 风控（发太快会被限制/封号）+ 多群同时说话**。数字必须重算 —— **但"有明确上限"这件事本身要抄** |
| **文件沙箱三模式** | 它的词汇表**本身就是文件操作**（文档原话："文件操作是完整的策略词汇——该 seam 不表达网络、进程、系统调用、设备或凭据限制"）。QQ bot 需要的能力词汇是"发文件/跑命令/改配置/读私聊/生图/发言"。搬**骨架**（策略逐调用传递 + 逐会话 fold + 失败关闭），不搬模式名 |
| **`sandbox_permissions` + `justification` 升权重试** | 绑定"模型可以重试一次完全相同的调用"。QQ bot 敏感操作的正解是**先问管理员**（异步，可能几分钟后才答），不是立刻重试 |
| **`defineTool` 的 schema DSL / `InferValue` / 类型化 SDK 生成** | 为"给模型看的类型化参数"服务。EggBloom 现有 12 个工具是硬编码 dict，**简单可控、无构建步骤**，在工具不多时引入 DSL 是过度设计。**但要抄一条**：工具输出分「规范值」+「渲染」两层，让日志与呈现解耦 |
| **profile/bundle 的 `cordis.patch.yml` 组合体系** | 为"多种分发形态 × 多种定制"而建。EggBloom 只有一个分发形态，再引入 patch 层会让配置变成五层。**要抄的只有那条坑**："**覆盖会替换整个设置块，不会自动合并**" |
| **plan mode（`exit_plan_mode` + 评审 UI）** | "先探索、提交计划、等批准"是编码任务的协作形态（副作用大且难撤销）。QQ bot 的对应场景**没有产品需求**，且它自己承认是"引导而非强制" |
| **ACP v1 作为控制面协议** | 那是编码 agent 生态（Zed 等）的标准。EggBloom 若要暴露控制面，应定义自己的或复用 OneBot/WebUI。**但"只暴露标准语义、不泄漏实现细节"的原则要抄** |

**一个反向印证值得注意**：DSH 把两个完全不同的私有钩子方言（Claude Code 30 个事件、Codex 10 个事件）都映射到**同一组 6 个内部扩展点**上 —— 说明**"扩展点"是一套被第三方生态验证过的稳定抽象**。而 **EggBloom 现有的 `PLUGIN_HOOKS` 已经是一组不错的扩展点**。值得做的不是重设计，而是：
① 保持稳定并文档化；② 补一份**共享规则**文档（明确规定「失败必须降级为受控结果、绝不向主循环抛异常」「合并规则」「事件只在轮次内」）；③ 用**同一组扩展点**适配未来的多个上游，而不是为每个适配器复制逻辑。

### 4.7 设计新 harness 时要逐条自问的 20 条不变量

调研文档附录 A 汇总了 DSH 的关键不变量。与 EggBloom 最相关的六条：

| # | 不变量 | 对 EggBloom 的意义 |
|---|---|---|
| **A1** | **模型可见即已记录** —— 任何到达模型请求的内容都必须能从日志重建 | 直接否定现在的"边算边存、构造 prompt 各写一遍" |
| **A4** | **失败关闭** —— 无法强制执行所请求的策略时拒绝执行，绝不静默放行 | 危险动作的默认行为必须是"拒绝"而不是"放过" |
| **A10** | **绝不向主循环抛异常** —— 每种失败模式降级为受控结果 | 现有插件的失败处理不统一 |
| **A15** | **每个可观察效果都通过事件发生** —— 内部实现绝不属于公开接口 | "干净"的定义 |
| **A18** | **`truncated` 是预算事实，不是上游完整性事实** | 截断与"没找到/没权限"必须是**不同字段**，不能混为一谈 |
| **A19** | **非人类生产方必须传入自己的 source，不能继承人类权限** | 插件/调度器发起的动作**不得**被当成管理员操作 |

### 4.8 五个开源 agent 的横向研究结论（opencode / Hermes / Claude Code / SWE-agent / OpenHands）

调研覆盖五个项目，提炼出 **12 条共性原则**与 **10 个分歧点**。这里只放与 EggBloom 直接相关的。

#### 12 条原则里最该记住的（其中几条**修正/加强**了我上面的设计）

| # | 原则 | 对 EggBloom 的意义 |
|---|---|---|
| 2 | **硬底线黑名单代码级硬编码**，在一切权限检查**之前**，不可被配置或 YOLO 覆盖 | 有些事不该有开关 |
| 3 | **无人值守场景默认拒绝危险操作**，而不是等问题超时 | **群聊就是无人值守** —— 与 DSH 的"升级重试"正好相反 |
| 4 | **记忆分两层**：小而有界的常驻（固定 token 成本）+ 大而无界的检索（**零 LLM 成本**） | 正好对应沙漏（检索）vs 人格注入卡（常驻） |
| 5 | **用户消息永不被摘要**；只压缩 agent 自己产生的内容 | 现在没有区分，压缩时可能把用户原话压掉 |
| 6 | **改写过已发送的历史 = 作废 prompt cache** → 做成默认关闭的开关 + 一个度量 | 加强 §4.2 的 KV Cache 那条；且**已有 `cache_hit_rate` 可度量** |
| 8 | **旧的工具结果是最先该丢的** —— 丢正文、留句柄 | 与 P5/P6 的有界保留 + spill 是同一件事 |
| 9 | **子代理的价值在上下文隔离，不在并行**；只回传摘要 + 独立预算 | 提醒：不要为了"并行"上子代理 |
| **11** | **从最小工具集起步**；模型变强后，**复杂脚手架的收益下降而维护成本不降** | ⚠️ **对"要不要做大 harness"的重要警告** —— 见下 |
| 12 | **工具调用顺序、角色交替、tool 对完整性是框架的责任**，模型不会替你维护 | |

> **第 11 条值得单独说**：它和我这份方案里"建一整套 harness"的倾向**是有张力的**。
> 结论不是放弃，而是**按收益÷成本排序、从最小的能用集合起步**（正好就是 §4.5 那个顺序）。
> 把"大而全的 harness"当目标，很可能做出一个维护成本高于收益的东西。

#### ★ 五件"这些项目都没解决、EggBloom 必须自己解决"的事

这是本次调研最有价值的产出 —— **它划出了真正属于 QQ bot 的设计空白**：

| # | 问题 | 为什么现成项目帮不上 |
|---|---|---|
| 1 | **自动的会话边界** | 群成员**不会主动 `/new`**。编码 agent 靠用户显式开新会话，QQ 群里没人会这么做 |
| 2 | **多人并发输入的归并策略** | Hermes 只解决了**单用户连发**；QQ 群里是多个人同时在说，需要决定"把哪些合并成一次上下文、说话人如何标注" |
| 3 | **按 QQ 用户 / 群的成本归因与配额** | 关键洞察：**操作者 ≠ 使用者 ≠ 付费者**。你付钱，群友在用。现成项目没有这个概念 |
| 4 | **无斜杠命令的 skill 触发** | 普通 QQ 群**没有 `/` 命令**。技能只能靠自然语言意图识别触发 |
| 5 | **群聊可见性策略** | 什么在群里说、什么私聊、什么静默 —— 现成项目全是"一对一"的 |

**这五条应当成为 harness 设计稿的核心章节**，而不是从 DSH 抄来的通用模式。
通用模式解决"怎么跑得高效"，这五条解决"在这群人和这个场景下该不该跑、为谁跑、花谁的钱"。

### 4.9 ★ Hermes 是唯一原生支持 QQ Bot 的参照物（应当作为首要蓝本）

调研确认：**Hermes Agent = `NousResearch/hermes-agent`**（独立开源 harness，Python/MIT，**不是** Hermes 模型系列）。
依据：官方文档站自述 + 独立 Developer Guide（Architecture / Agent Loop / Tools Runtime / Context Compression —— 只有 harness 才会写这类文档）+ 目录树含 `run_agent.py`、`tools/registry.py`、`gateway/platforms/`。

> **关键：它是本次研究的五个项目里唯一原生支持 QQ Bot 的** —— `gateway/platforms/` 里有 `qqbot`，官方平台表有 QQ 行。

**它恰好解决了 §4.8 那五件"没人解决的事"里的三件**，这是本方案最有价值的借鉴：

#### ① 双层记忆 —— 直接解决"群聊历史极长"

| 层 | 实现 | 特点 |
|---|---|---|
| **有界常驻** | `MEMORY.md`（2200 字符）+ `USER.md`（1375 字符）常驻 system prompt | **~1300 token 固定成本**，可预测 |
| **无界检索** | `session_search` 走 **SQLite FTS5** | **~20ms、零 LLM 成本、返回真实消息而非摘要** |

配套纪律：超限时**返回错误强制 agent 当场合并**；条目做注入扫描。

> **对 EggBloom 的意义**：沙漏**已经有 FTS5**（`sandglass.db`）—— 也就是说**"零成本检索历史"这件事的基础设施已经在你手里了**，
> 只是没被接到 prompt 组装链上。这一条与现有架构**天然契合**，是投入产出比最高的借鉴点。

#### ② 无人值守策略档 —— 直接否定"危险操作问管理员"

- `cron_mode` / `single_query_mode` / `unattended_mode` **默认全 deny**，且**立即阻断而不是等 300s 超时**
  （理由：无人值守时**根本没人能回 `/approve`**）
- 授权检查六步**默认拒绝**；Admin 与普通用户按**平台 + 作用域**独立分档
- DM pairing：8 字符码 / 密码学随机 / 1h TTL / 限流 / 锁定 / 0600 权限

> ⚠️ **修正我在 §4.6 的说法**：我原写"QQ bot 敏感操作的正解是先问管理员（异步）"。
> 研究表明这个模型**在群里根本不成立** —— 消息在流动、没人盯屏、超时了也没人答。
> **正解是能力白名单 + 默认拒绝**，而不是审批等待。

#### ③ 投递可靠性三件套 —— 直接解决"多人并发"与"什么时候别说话"

| 机制 | 做法 |
|---|---|
| **delivery ledger** | at-least-once：**重投而不重跑**；模糊性**显式标注**（`♻️ Recovered reply — may be a duplicate`）而非静默重发；流控惩罚**持久化**；3 次/24h 有界重试 |
| **静默令牌** | `[SILENT]` / `[静默]` / 沉默 —— **整个响应必须恰好是令牌**才抑制投递；真人消息里的裸令牌**替换成简短通知**；失败仍浮出为错误；**transcript 仍保留该轮次** |
| **busy-input 三模式** | `interrupt` / `queue` / `steer`，**去抖 0.35s / 硬上限 1.0s** |

> 这三件是**永久在线多人群聊的刚需**，而且直击 §4.8 的空白 #2（多人并发归并）与 #5（群聊可见性策略）。
> 尤其"静默令牌"：它把"要不要说话"从**隐式行为**变成了**可记录、可回放、可测试的显式产物** —— 与 A1「模型可见即已记录」完全一致。

### 4.10 明确"不要照搬"的清单（研究另列 10 条）

| 不要 | 原因 |
|---|---|
| 用模型名当稳定的窗口属性 | 模型会变，属性不该跟着变 |
| 70+ 工具 | 模型选择会退化 |
| **假设「一条消息 = 一个轮次」** | QQ 群里多人在说，这个假设直接错 |
| 单用户 CLI 的 Tab / Shift+Tab 隐含状态 | 群里没有键盘交互 |
| 单用户连发的归并策略 | 那是 Hermes 解决的版本；QQ 群是**多用户**并发 |
| 把 system prompt 在会话中途改动 | 会作废整个 prompt cache（Claude Code 的 `/reload-mcp` 就是这个坑） |

## 五、前端落地

### 5.1 规范已定稿
`docs/DESIGN_SYSTEM.md`：无盒 / 字级 / 裸露 / 活性 四原则；七大原语（`stat` `kv` `cmd` `fld` `row` `sig` `log`，卡片不在其中）；
**动态效果九条**（其中「连接呼吸 —— 该呼吸的不呼吸了就是出事了」是灵魂）；
铁律「图形必须承载数据，删掉它信息不丢就删掉它」。

### 5.2 坐标已校正（本方案更正）
- 全文件 **19** 个 `class="card"`、**18** 个 `panel`、24 个 `panel-title`
- **430 处内联 `style=`** ← **这才是"AI 味"的真源头**
- 最重的页面：协议页 25,562 字符、群管理 16,991、表情包 15,010、生图 11,951
- **仪表盘其实很小（1,757 字符、0 卡片）** —— 我之前说它 30K/9 卡片是错的

### 5.3 迁移方法（保证功能 100% 不变）
1. **先出红线清单**：扫出 JS 依赖的所有 `id` / `class` / `data-*` / 内联 `onclick` 函数名 —— 这些名称与层级不得变（调研已在进行）
2. **JS 逻辑一行不改**：只动 `<style>` 与模板里的 class、容器层级
3. **逐页迁移**，顺序按「重 → 轻」：协议 → 群管理 → 表情包 → 生图 → 群聊行为 → Token → 配置中心 → Bot → 日志控制 → 仪表盘 → 通知 → 记忆 → 底层控制 → 插件
4. **每页一次 git 提交** + 跑一次该页交互清单
5. **先出样张图评审**（Playwright 渲染 PNG），满意后再动真文件
