## 1.3 ★ 已核实的硬事实（这些坑我们踩过，别再踩）

### (1) 动作数量：**190 / 25 / 165**，且极易数错

| | |
|---|---|
| SnowLuma 提供 | **190 个动作** |
| EggBloom 实际调用 | **25 个（13.2%）** |
| 从未使用 | **165 个** |

**为什么容易数错**：SnowLuma 用**四种 wrapper** 定义动作 ——
`defineAction` 直定 125 + `groupAction`（**注入 `group_id`**）53 + `groupUserAction`（注入 `group_id`+`user_id`）7 + `defineStreamAction` 5 = **190**。
**只抓 `defineAction` 会漏掉 60 个动作，其中包括 `send_group_msg`、`set_group_ban` 这些核心动作。**

190 这个数字的权威来源：源文件 `E:\SnowLuma-v1.14.10-win-x64\config-k6rruub-.js` 里的官方注册表 `ACTION_GROUPS`（第 11855–11904 行），分类合计逐一加总。

**完整动作契约见 `docs/plan/snowluma-actions.md`（105 KB，含每个动作的逐参数表）。不要去重新提取。**

### (2) 调用约定：**动作名就是 HTTP 端点名**

`action = url.pathname 去掉配置的 path 前缀`（`index.mjs:216412-216419`）。
本机 `config/onebot.json` 是 `path:"/"` + `port:3000` → **`POST http://127.0.0.1:3000/<动作名>`**。
也支持根路径 + body `{action, params, echo}`、GET 查询串、表单；仅 GET/POST。
响应：`{status, retcode, data, message, wording, echo}`。

**在插件里直接用 `ctx.api_call(action, params)` 即可**（ABI v2 已就绪），无需任何底层开发。

### (3) 两个"照抄就失败"的动作名

- **`delete_group_album_media` 不存在** —— 真名是 **`del_group_album_media`**（源文件第 8761 行）
- **`set_group_todo` / `complete_group_todo` / `cancel_group_todo` 的 `message_id` 必须是本进程缓存过的群消息**（源文件 `groupTodoRun`:5864），否则失败。**必须先用 `get_group_todo_list` 取 id。**

### (4) 真插件 ABI 的钩子只接了一半

| typed 钩子 | `bot_core` 是否派发 |
|---|---|
| `on_message` | ✅ 2 处（6830 / 6834） |
| **`on_before_reply`** | ❌ **0 处** |
| **`on_after_reply`** | ❌ **0 处** |
| `on_event` | ✅（由 `ctx.emit` 驱动，不走 bot_core） |

旧式钩子（`PLUGIN_META`）有 5 处派发：**159 / 6141 / 6261 / 6476 / 7431**。
**harness 要往 prompt 注入内容，必须先修这个缺口（见任务 6）。**

### (5) 项目里有两套 `/api/*`，且都有 `/api/status`

- `webui_server.py` → **8080**（浏览器/Electron），**51 条唯一路由**
- `bot_core.py` → **3005**（协议层推送 + 联系人管理 API），**11 条**

**前端「联系人管理 / 群管理」打的是 3005 那套。排障时先分清端口。**

### (6) 端口顺延与 Electron 断裂（已知缺陷，未修）

后端 `pick_port`（`webui_server.py:4001`）在 8080 被占用时会顺延并写 `last_port.txt`，
但 `main.js` 把 URL **写死**成 `localhost:8080`（169 / 173 / 306）且从不读该文件。
→ 一旦顺延，Electron 窗口会按 `did-fail-load` 每 2 秒重试 8080 **永远出不来**，而服务其实正常。

### (7) 几个"看起来在工作、其实没生效"的功能（已核实，未修）

| 现象 | 证据 |
|---|---|
| EGO 情绪温度无效 | `personality_temperature` 一路透传（5659→5184→5882/5892），但 `_call_chat_sync:5578` 只用全局 `AI_TEMPERATURE` |
| 私聊画像未生效 | `private_memory_context` 唯一调用点传空串（7377 / 7413） |
| 群聊**没有白名单** | 群分支只查 `reply_enabled`（6862-6870），适配器转发全部事件 → **Bot 所在的任何群都会参与回复** |
| 多个锁从未使用 | `_replies_lock` / `_meme_lock` / `_group_meta_lock`；`_buffer_lock` 只在一处用，而缓冲写入与 Timer 线程 `pop` 都不加锁 |
| `save_state` 吞掉失败 | 裸 `except: pass`（1893） |

### (8) 两条已核实的安全问题（影响面已如实标注，**不要夸大**）

- **`/memes/*` 缺路径校验**：静态分支有 `resolve()` + 前缀校验 + 扩展名白名单，但**判定失败后不 `return`**，控制流落到 2311 的 memes 分支；而 `_serve_meme`（1148-1174）是裸的 `meme_dir / rel`。上溯两级可读 `resources/app/` 下任意文件（含 `bot_config.json` 里的 `onebot_token`）。
  **但**该响应不带 ACAO、Host 校验挡 DNS rebinding → **属加固缺陷，不是远程可利用漏洞。**
- **`GET /api/plugins/action` 的 CSRF 面**：它在 `do_GET`（1512）也被处理、参数从 query 取，而 Origin 闸门只加在 `do_POST`（2339）→ **GET 路径漏了。**

## 任务 5 harness 前三项（**按收益÷成本，全部低成本**）

> **⚠️ 研究里有一条重要警告：「从最小工具集起步；模型变强后，复杂脚手架的收益下降而维护成本不降」。**
> 所以**严格按这个顺序做，做完一项验证一项，不要一次性铺开。**

### 5.1 策略快照追加（保住前缀缓存）—— 最小改动、最大收益

**做什么**：把"模式/权限/人格档位切换时**改写**系统提示词静态段"改成"**追加**一份完整快照到保留历史之后"，让静态段保持**逐字节稳定**。

**为什么**：改写过已发送的历史 = **作废 prompt cache**。DSH 明写"模式切换时稳定系统提示词仍逐字节相同"。

**验证手段现成**：`token_stats.py:89` 与 `:100` 已经在算 **`cache_hit_rate`**；
`bot_core.py:5843-5844` 从 LLM usage 里读 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。
→ **做完前后对比 `cache_hit_rate`，这是硬指标。**
`prompt_cache_hit_token` 是 DeepSeek 的 usage 字段，本机模型走的就是 DeepSeek 系。

### 5.2 有界保留原语 + spill 落盘

**做什么**：两个纯函数 + 一个落盘目录 + 一个读取入口。

| 原语 | 行为 |
|---|---|
| `ItemRetainer` | 保留前 N 项，**持续 drain 以得到精确省略计数**（不是"大约丢了 20 条"，是准确数字） |
| `TextRetainer` | **按字节**取 head/tail，内存有界，**在每个切割处修剪不完整码点**（中文场景关键 —— 不然会切出乱码） |

**超预算内容**：落盘 + 内联首尾预览 + **绝对路径** + 读取提示。

**硬纪律**：`truncated` 是**预算事实**，绝不表示"没搜到 / 没权限" —— **两者必须是不同字段**。

### 5.3 事件溯源会话日志（**先只覆盖一个群的对话历史做试点**）

**做什么**：把"边算边存、构造 prompt 时各写一遍"改成**仅追加日志 + 从日志派生请求**。

**铁律**：**模型可见即已记录** —— 任何到达模型请求的内容都必须能从日志重建。

**为什么先只做一个群**：这是三项里改动最大的，试点能控制爆炸半径。

### 验收（三项各自）
- [ ] 5.1：`cache_hit_rate` **有可观测的提升**（贴前后数字进 commit message）
- [ ] 5.2：写单测覆盖「中文在切割点被切成半个字」这个 case；`truncated` 与"未找到"是不同字段
- [ ] 5.3：一个群的对话历史能**从日志完整回放**，且回放结果与实际发给模型的一致
- [ ] **每项一次独立 commit**（不要混在一起）

## 任务 6 修 ABI 缺口（**harness 注入 prompt 的前置条件**）

**问题**：typed `on_before_reply` / `on_after_reply` 在 `bot_core` **0 处派发**，而旧式钩子有 5 处（**159 / 6141 / 6261 / 6476 / 7431**）。
→ **用真插件 ABI 写的插件无法干预 AI 回复**，而这是往 prompt 注入内容的唯一途径。

**做法**（细则见 `docs/CORE_FLOW.md` 第五节）：
1. 在上述 **5 个旧式派发点并列补一次 typed 派发**（`pm.execute_typed_hooks("on_before_reply", event={...})`）
2. **必须在 `6263` 同一处聚合** —— 否则两套钩子的 `skip`/`inject` 会打架
3. 注入契约：返回 `{"action": "skip" | "inject", ...}`，按插件 `priority` 聚合

**⚠️ 注意**：研究明确指出 **拦截器不要改写 `event["text"]`**（DSH 明令禁止 pre-execute 改写参数），否则日志与实跑不一致。

- [ ] **现有 5 个旧式钩子的行为完全不变**（跑插件回归：`ego` / `group_chat_decider` / `web_search` / `web_operator` 全部正常加载）

`docs/plan/dsh-harness-design.md` 第 11.3 节有 **15 项按收益÷成本排序的完整清单**。第 5、6 项之后的顺序：

| 9 | 压缩的事务化 + 结构化检查点（**依赖 5.3**） |

### ⚠️ 明确的"**不要搬**"清单（研究列了 19 项，这里挑最关键的）

| 不要搬 | 原因 |
|---|---|
| **PTC（让模型写代码调工具）** | QQ bot 调用链只有 1–3 步，function calling 更可靠；且 PTC 的中间值**无法从会话回放重建、可能耗尽内存** —— 对永久在线 bot 是**稳定性风险** |
| **压缩的阈值与段名**（`0.8` / `65536` / `Files and Code`） | 按 128k+ 长编码会话标定。**QQ bot 每个群是独立小会话**，照抄会**过度压缩**。只搬结构，数字必须重标 |
| **`goal` 的「空闲就自动续跑」** | 对永久在线、多人共享的 QQ bot 是**危险行为**（会无人干预地连续行动最多 256 轮） |
| **并发默认值**（`maxParallelToolCalls=10` / `maxActiveSubagents=8` / `maxTotalAgents=1000`） | 为"单用户本地编码、要跑满 CPU"标定。QQ bot 的约束来自 **LLM rate limit + QQ 风控 + 多群同时说话**，必须重算。**但"有明确上限"这件事要抄** |
| **文件沙箱三模式** | 它的词汇表**本身就是文件操作**。QQ bot 需要的能力词汇是"发文件/跑命令/改配置/读私聊/生图/发言"。搬**骨架**（策略逐调用传递 + 逐会话 fold + 失败关闭），不搬模式名 |
| **`sandbox_permissions` + `justification` 升权重试** | 绑定"模型可重试一次相同调用"。**QQ bot 敏感操作的正解是能力白名单 + 默认拒绝**，不是审批等待（群里根本没人能回 `/approve`） |
| **plan mode / ACP v1 / patch 组合体系** | 都是编码 agent 生态的形态，QQ bot 没有对应产品需求 |

### ★ 最值得借鉴的一条：Hermes（唯一的 QQ 原生参照物）

调研确认 **Hermes = `NousResearch/hermes-agent`**（独立开源 harness，不是模型系列），
**是五个参照项目里唯一原生支持 QQ Bot 的**（`gateway/platforms/qqbot`）。

它恰好解决了研究指出的"五件现成项目都没解决的事"里的三件：

| 机制 | 解决什么 |
|---|---|
| **双层记忆**：`MEMORY.md`(2200 字符) + `USER.md`(1375 字符) 有界常驻 system prompt（**~1300 token 固定成本**）+ `session_search` 走 **SQLite FTS5**（**~20ms、零 LLM 成本、返回真实消息不摘要**） | 群聊历史极长 |
| **无人值守策略档**：默认全 deny + **立即阻断而非等 300s 超时**；Admin/User 按平台+作用域分档 | 危险操作审批在群里**不成立** |
| **投递可靠性三件套**：delivery ledger（at-least-once，**重投不重跑**，模糊性显式标注 `♻️ Recovered reply — may be a duplicate`）+ **静默令牌**（`[SILENT]`，**整个响应恰好是令牌才抑制**，真人消息里的裸令牌替换成通知）+ busy-input 三模式（`interrupt`/`queue`/`steer`，去抖 0.35s / 硬上限 1.0s） | 多人并发归并 + 群聊可见性 |

> **★ 投入产出比最高的借鉴点**：**沙漏已经有 FTS5 了**（`.neurobase/sandglass.db`）——
> "零成本检索历史"的基础设施**已经在手里**，只是没接到 prompt 组装链上。

### ★ 五件"必须自己解决"的事（现成项目都没解决）

这是 harness 设计稿的核心章节，也是真正属于 QQ bot 的空白：

1. **自动的会话边界**（群成员**不会主动 `/new`**）
2. **多人并发输入的归并策略**（Hermes 只解决了单用户连发）
3. **按 QQ 用户/群的成本归因与配额** —— 关键洞察：**操作者 ≠ 使用者 ≠ 付费者**（用户付钱，群友在用）
4. **无斜杠命令的 skill 触发**（普通 QQ 群没有 `/` 命令）
5. **群聊可见性策略**（什么在群里说、什么私聊、什么静默）

### ★ 一条反向印证（关于现有插件体系）

DSH 把两个完全不同的私有钩子方言（Claude Code 30 个事件、Codex 10 个事件）都映射到**同一组 6 个内部扩展点**上
—— 说明"扩展点"是一套被第三方生态验证过的稳定抽象。
**EggBloom 现有的 `PLUGIN_HOOKS` 已经是一组不错的扩展点。**
值得做的不是重设计，而是：① 保持稳定并文档化；② 补一份**共享规则**文档（明确「失败必须降级为受控结果、绝不向主循环抛异常」「合并规则」「事件只在轮次内」）；③ 用同一组扩展点适配未来的多个上游。

# 5. 通用交付规范

1. **一次任务一次 commit**，commit message 写清「改了什么 + 为什么 + 怎么验证的」
2. **改动前先 `git status` 确认工作树干净**（起点应该是干净的）
3. **改完运行副本**：先 `sync-dist.ps1 -DryRun` 看清单，确认后去掉 `-DryRun`
4. **每次改动后至少跑这三条回归**：
   ```powershell
   # ① 主程序能导入（会真实启动插件系统，能顺带验证插件）
   cd "E:\EggBloom水星\EggBloom Desktop-new\resources\app"; python -c "import bot_core"
   # ② 蒸馏插件测试套件
   cd "plugins\这样脆弱的东西"; python -m tests.run_all
   # ③ 插件 ABI 自检
   cd "D:\git\EggBloom"; python tests\test_plugin_abi_v2.py
   # ④ 调度器自检
   python tests\test_scheduler.py
   ```
5. **`python -c "import bot_core"` 会拉起 llama-server 嵌入服务** —— 测完记得清理：
   ```powershell
   Get-CimInstance Win32_Process | Where-Object { $_.Name -match 'llama-server' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
   ```
6. **拿不准的写"未能确认"，不要猜** —— 这条在本次整理中被反复证明是对的（我因为猜数字错了两次）
