## 1. 项目概述

### 1.1 目标

从聊天记录、对话记忆、落沙数据中提取人格模型，按数据量分级蒸馏（L0-L4），生成通用人格文件格式（Persona-File v1.0）。

### 1.2 核心能力

- **人格蒸馏**：从多种数据源提取人格特征，按数据量分级蒸馏
- **分级体系**：L0-L4 五级，每级有明确的数据量门槛和 Token 预算
- **人工审核**：蒸馏完成后特征提取结果需人工审核才能保存
- **溯源项链**：每条关键声明附带数据来源标识
- **置信度评分**：每条声明附带 0-1 置信度
- **伦理合规**：严格遵循伦理协议，审计日志可追踪

### 1.3 设计约束

1. 不绑定任何单一平台，可作为通用人格表示格式
2. 每个 section 有独立 token 预算，总 token = 各 section 之和
3. 逐层递进，L{n} 包含所有 <n 的 section
4. 每条关键声明附带溯源标识
5. 每条声明附带 0-1 置信度
6. 人类可读（Markdown）+ 机器可解析（内嵌 JSON）

### 1.4 关键决策

| 决策项 | 内容 |
|--------|------|
| 插件形态 | 真插件 ABI v1，PLUGIN_SPEC=1 |
| 蒸馏目标 | 两者都要（任意第三人 + 主人） |
| 准确率标准 | 图灵测试通过率 |
| Ponytail | 写代码的编程规范，不是插件功能 |
| 伦理 | 有完整伦理协议，审计日志可追踪 |
| Token 量级 | 200K-20M+（百万到千万级） |
| 人格文件 | 通用格式，不绑定 EggBloom |
| 蒸馏后用途 | 不重要（用户明确说不需要预设用途） |

## 2. EggBloom Desktop 架构分析

### 2.1 产品定位

EggBloom Desktop 是一个 QQ AI 智能助手，基于 OneBot v11 协议，Python 后端 + Electron 外壳。

### 2.2 两套并行的人格/记忆系统

| 系统 | 定位 | 核心文件 |
|------|------|----------|
| **EGO 插件** (`plugins/ego/`) | QQ 对话面的人格+记忆 | personality_engine / super_memory / chat_style / mood_engine / slang_learner |
| **沙漏记忆** (`sandglass_lite.py`) | 深层记忆 + 决策粒子 | sandglass.txt 落沙 → 原文检索（倒排 + 密度×信任） → 按日期回忆 → 决策粒子 |

### 3.1 插件结构

```

├── level_classifier.py      # 数据量分级判定
├── data_collector.py        # 数据收集（chat_logs/sandglass/super_memory/私聊记忆）
├── feature_extractor.py     # L1 原子特征提取
├── pattern_analyzer.py      # L2 模式整合
├── personality_model.py     # L3 人格模型生成 + prompt 注入
├── review_manager.py        # 人工审核管理
├── turing_validator.py      # 图灵测试验证
├── audit_logger.py          # 审计日志

    ├── config.json          # 插件配置
    ├── pending_review.json  # 待审核的蒸馏结果
    ├── distills/            # 每人一份蒸馏结果
```

> **命名约定（v1.0 定稿）**：插件目录名 = manifest name = plugin_id = "这样脆弱的东西"，
> 三者全对齐，保证 WebUI 页面加载（`/page?plugin_id=这样脆弱的东西`）、
> 启停切换（`pm.enable("这样脆弱的东西")`）、动作通道（`/api/plugins/action`）全部走同一个键。
> Python 3.10+ 支持中文模块名导入（已实测通过）。

## 4. 数据量分级体系

### 4.1 等级-Token 矩阵

| 等级 | 名称 | 数据量 | Token 预算 | 人格完整度 | 中文等效 |
|------|------|--------|-----------|-----------|---------|
| L0 | 种子 Seed | <100 条 | **200K** | 能说出"这人大概是什么样" | ~30万字，一部长篇 |
| L1 | 核心 Core | 100-1K 条 | **500K** | 日常对话风格可匹配 | ~75万字，三部长篇 |
| L2 | 深度 Deep | 1K-10K 条 | **2M** | 跨话题人格稳定 | ~300万字，一整套丛书 |
| L3 | 完整 Complete | 10K-50K 条 | **5M** | 人格模型可对话 | ~750万字，一个小图书馆 |
| L4 | 完美 Perfect | 50K+ 条 | **20M+** | 图灵测试级还原 | ~3000万字，大型知识体系 |

### 4.2 分级递进规则

```
L0 ──→ S0 + S1                    (200K tokens)
L1 ──→ S0 + S1 + S2 + S3         (500K tokens)
L2 ──→ S0 + S1 + S2 + S3 + S4 + S5 (2M tokens)
L3 ──→ S0 + S1 + S2 + S3 + S4 + S5 + S6 + S7 (5M tokens)
L4 ──→ S0-S11 全部               (20M+ tokens)
```

### 4.3 自动分级判定

```python
def classify_level(data_count: int) -> str:
    if data_count < 100:
        return "L0"
    elif data_count < 1000:
        return "L1"
    elif data_count < 10000:
        return "L2"
    elif data_count < 50000:
        return "L3"
    else:
        return "L4"
```

### 4.4 Token 注入策略

| 模型上下文 | 注入策略 | Token 消耗 | 覆盖 section |
|-----------|---------|-----------|-------------|
| 8K-32K | 仅 S1 身份 | ~200K → 压缩到 5K | S1 摘要 |
| 32K-128K | S1+S2 语言 | ~500K → 压缩到 30K | S1+S2 摘要 |
| 128K-256K | S1-S3 行为 | ~500K → 压缩到 100K | S1-S3 摘要 |
| 256K-1M | S1-S5 认知+关系 | ~2M → 压缩到 500K | S1-S5 摘要 |
| 1M+ | 全量注入 | 全量 20M+ | S0-S11 |

**压缩策略**：当模型上下文不足以承载全量人格文件时，按优先级压缩：
1. 保留核心声明（置信度 > 0.7）
2. 丢弃低置信度声明
3. 合并相似声明
4. 保留溯源链接（但不注入到 prompt）

## 5. 人格文件格式 Persona-File v1.0

### 5.1 设计原则

1. 不绑定任何单一平台，可作为通用人格表示格式
2. 每个 section 有独立 token 预算，总 token = 各 section 之和
3. 逐层递进，L{n} 包含所有 <n 的 section
4. 每条关键声明附带溯源标识
5. 每条声明附带 0-1 置信度
6. 人类可读（Markdown）+ 机器可解析（内嵌 JSON）

### 5.2 理论基础

| 学科 | 框架 | 贡献维度 |
|------|------|---------|
| 人格心理学 | Big Five (OCEAN) | 开放性/尽责性/外向性/宜人性/神经质 |
| 认知心理学 | 决策模式 | 理性/感性/直觉/权衡 |
| 情感心理学 | 情绪智力 | 情绪表达/情绪识别/情绪调节 |
| 社会心理学 | 依恋理论 | 安全型/焦虑型/回避型 |
| 语言学 | 风格语言学 | 词汇/句法/语篇/元话语 |
| 文化人类学 | 文化标记 | 梗/方言/时代特征 |

### 5.3 完整结构（12 个 section）

#### S0 元数据 Metadata（所有等级，~10K tokens）

```json
{
  "standard": "Persona-File/v1.0",
  "version": "1.0",
  "level": "L{n}",
  "target": "{name_or_id}",
  "token_budget": {budget},
  "actual_tokens": {actual},
  "confidence_overall": {0.0-1.0},
  "distilled_at": "{iso_timestamp}",
  "data_span": "{start} ~ {end}",
  "sources": [{"type": "...", "count": n}],
  "distiller": "这样脆弱的东西/v{version}",
  "ponytail_compliance": true,
  "ethics_version": "v1.0"
}
```

#### S1 身份层 Identity（L0+，~190K tokens）

- 核心身份锚点：姓名/称呼、年龄段、性别表达、角色定位、社会身份
- Big Five 完整评分：每个维度含原始得分、置信区间、行为证据链
- MBTI 推断：四维推断（含不确定度标注）
- 一句话人设：50字
- 身份演化史：早期→中期→当前（含转折点和证据）
- 多面性：不同场景下的身份切换（工作/社交/独处/冲突）

#### S2 语言层 Linguistics（L1+，~490K tokens）

- 词汇指纹：高频词 Top-500（含频率、上下文、首次出现）、低频但特征词、禁用词/回避词、黑话/俚语、双语切换模式、创造词/自造词
- 句法结构：平均句长+标准差+分位数、句式偏好分布、开头模式 Top-50、结尾语气 Top-50、标点习惯全表、断句风格、句式变换频率
- 表情系统：高频表情 Top-50、颜文字风格图谱、特殊符号偏好、表情使用密度（分场景）、表情组合模式
- 回复模式：长度分布（直方图数据）、延迟分布、单条vs连发比、引用/回复习惯、消息切分模式
- 语域切换：正式/非正式/专业/口语的切换规则和场景
- 语气词体系：全部语气词+使用频率+场景+情绪关联

#### S3 行为层 Behavior（L1+，~100K tokens）

- 话题偏好图谱：全部话题（参与度 0-1、典型反应、数据支撑条数）
- 情绪模式：分布比例、触发词（正/负）、表达风格、调节策略、衰减速度、传染倾向、情绪与场景关联矩阵
- 幽默与讽刺：类型分布、频率、边界规则、典型样本 Top-100
- 冲突处理：反应模式、愤怒表达、道歉模式、冷战倾向、升级/降级路径
- 对话节奏：主动/被动频率、插话倾向、沉默偏好场景、话题转换模式、节奏变化
- 社交模式：群聊vs私聊行为对比、群体角色、从众倾向、意见表达、社交能量消耗/恢复

#### S4 认知层 Cognition（L2+，~1M tokens）

- 价值观体系：全部价值观（强度、排序、证据、冲突价值观对）
- 决策模式：风格、路径、速度、后悔倾向、风险偏好、决策后悔案例 Top-50
- 认知矛盾：全部矛盾对（表现A vs B、触发条件、强度、证据）
- 驱动力：主要/次要/终极（含演化轨迹）
- 雷区与禁区：全部（话题/语言/行为，严重程度、触发后果、规避策略）
- 知识领域：擅长/了解/无知/学习倾向（含具体领域列表和深度评分）
- 时间感知：作息模式（分时段）、时间取向、拖延倾向、截止日期敏感度、时间管理策略
- 思维风格：分析/直觉/系统/发散/收敛的偏好分布
- 信息处理：信息获取偏好、信息筛选策略、记忆模式、注意力分配

#### S5 关系层 Relationship（L2+，含在 2M 预算内）

- 依恋风格：类型、特征、安全感来源、不安全感触发、依恋行为模式
- 关系图谱：全部关系对象（类型、频率、强度、典型互动、演化轨迹）
- 亲密度表达：分对象（亲昵表达、距离感维护、社交面具）
- 群体行为：角色、从众倾向、意见表达、冲突解决、群体身份认同
- 人际关系策略：讨好/回避/对抗/妥协的分布和触发条件
- 信任建立：速度、条件、破坏因素、修复能力

#### S6 时间层 Temporal（L3+，~2.5M tokens）

- 日常节律：24小时行为分布、工作/休息/社交时间分配
- 周期模式：工作日vs周末、季节变化、年度周期
- 生命周期阶段：早期/中期/当前的行为对比
- 时间演化轨迹：关键转折点列表（日期、事件、变化、证据）
- 习惯稳定性：习惯形成速度、习惯维持强度、习惯打破条件
- 时间压力响应：截止日期/突发事件/多任务并行时的行为变化

#### S7 环境层 Environmental（L3+，含在 5M 预算内）

- 场景切换：工作/社交/独处/线上/线下/游戏/学习的行为对比
- 设备偏好：手机/电脑/平板的使用场景和行为差异
- 空间偏好：线上vs线下、私聊vs群聊、公开vs私密
- 文化环境：方言/地域文化/网络文化的影响
- 社交环境：不同社交圈的行为调整
- 情绪环境：周围环境情绪对自己的影响

#### S8 完整重建 Complete Reconstruction（L4+，~15M tokens）

## 6. 蒸馏管线设计

### 6.1 六级流水线（v2）

```
L0 捕获 → L1 基线 → L2 取证 → L3 定稿 → L4 对账 → 构建
  ↓         ↓         ↓         ↓         ↓        ↓
原始记录  量化特征  逐层捞观察  合并校验  送回原文  人格文件
 +编号      +证据     （不抽样）  +重估置信 逐条判定  +注入卡
```

每一级都在做上一级做不到的事，**没有任何一级是装饰**。

### 6.2 阶段详解

#### 阶段 0：L0 捕获（Capture）

- 解析 chat_logs / super_memory / sandglass / private_memory，提取目标人的所有消息
- 剥离平台痕迹（`[引用]` 前缀）、URL 前方截断，标记噪声与链接
- **给每条消息编号**（M0001…），跨源合并同一次发言，单独统计同渠道真实重复
- 统计消息数、字数、跨度、时段分布，判定等级与可行性

#### 阶段 1：L1 基线（Baseline，启发式，零成本）

- 语言层：n-gram 词频（带频次与出现位置）、开头/结尾模式、标点、表情、语气词、句式长度
- 行为层：话题命中、情绪、幽默、发问、丢链接、派活、重复发送、引用回复习惯
- 认知/关系/时间/环境层：诉求句、技术语境、亲昵称呼、活跃时段、时间跨度、来源渠道
- 模式整合：作息节律、周内分布、情绪基调、数据跨度、兴趣广度、消息切分、连发习惯、
  **样本充分度**
- **每条基线特征同样挂证据编号** —— 整份文件里没有一条"无主"的结论

#### 阶段 2：L2 取证（Evidence，LLM）

- 把**全量语料**（带编号与重复标注）投喂给模型，**不抽样**
- 按 `sections_per_call` 分批，每批只问指定的几层，附该层的取证指引
- 输出 `{"sections": {"<层名>": {"entries": [...]}}}`，每条带 evidence / counter / confidence

#### 阶段 3：L3 定稿（Consolidate，LLM）

- 把所有层的原始观察合并成**一次**调用：去重、剔无据、记矛盾、重估置信度
- 同时喂入 L1 统计基线，防止模型写下与硬事实打架的结论
- 与启发式基线合并：LLM 定稿在前，基线里未被覆盖的条目补在后

#### 阶段 4：L4 对账（Critic，LLM + 确定性校验）

- 终审：把整份结论清单送回原文**逐条判定** supported / weak / unsupported
  - unsupported → 剔除；weak → 置信度 ×0.7；并补出遗漏的明显特征
- 确定性校验（不依赖模型）：校验全部引用编号是否存在
  - 声称有证据但编号全不存在 → 判为编造，剔除
  - 部分不存在 → 置信度 ×0.6 并标记

#### 阶段 5：构建（Build）

- 渲染 Persona-File v1.0：按等级输出对应 section，每条附引用编号与原文引证
- 生成「人格注入卡」：可直接作为 system prompt 喂给任意模型
- 计算人格指纹、写审计、进入人工审核

### 6.3 人工审核环节

蒸馏完成后不直接保存，进入人工审核：

```
蒸馏完成 → 人工审核 → 审核通过 → 保存人格文件
              ↓
           丢弃 / 重新蒸馏
```

审核界面支持：编辑特征值、调整置信度、删除错误项、添加遗漏项、
**查看每条结论的引用编号与来源（统计 / AI / 终检）**、一键复制人格注入卡。

## 7. 伦理协议

### 7.1 核心原则

1. **自主权**：被蒸馏对象的人格数据主权归其本人所有
2. **最小必要**：只收集蒸馏所需的最少数据
3. **可撤回**：任何时刻可撤回授权并删除全部数据
4. **不可滥用**：蒸馏结果不得用于歧视、操控或伤害

### 7.2 知情同意

- 原则上蒸馏前必须获得被蒸馏者的明确知情同意
- 例外：蒸馏执行者本人、公开数据、已明确授权第三方
- 14岁以下未成年人需监护人同意

### 7.3 数据范围

允许的数据源：本人提供、公开发布、授权第三方、公开文本
禁止的数据源：黑客获取、欺骗获取、胁迫获取、明确声明为私密的数据

### 7.4 敏感信息处理

身份信息、健康信息、财务信息、政治立场、性取向、宗教信息、位置信息、生物特征——必须脱敏或排除。

### 7.5 数据存储

- 本地优先，加密存储
- 最小化存储，不保留原始数据副本
- 不同被蒸馏者的数据隔离存储

### 7.6 数据删除

被蒸馏者有权在任何时间要求删除。收到删除请求后 30 天内完成。

### 7.7 使用限制

禁止用途：冒充欺诈、操控决策、商业牟利（未授权）、歧视性决策、武器化使用、深度伪造。

### 7.8 审计追踪

每次蒸馏操作必须记录审计日志，保留至少 2 年。

详见 `ETHICS.md`。

## 10. Ponytail 编程规范

### 10.1 核心原则

Ponytail 是**写代码的编程规范**，不是插件功能。

| 原则 | 应用 |
|------|------|
| YAGNI | 不写当前不需要的功能 |
| 复用 | 直接 import EGO 的函数，不重复造轮子（沙漏侧走 `sandglass_lite`） |
| 标准库 | 只用 json/sqlite3/re/os/time，不引入第三方依赖 |
| 原生 | 用 EggBloom 的 ctx.ai_chat / ctx.get_state / ctx.emit |
| 一行搞定 | 能用一行解决的不写三行 |
| 极简 | 先跑通最小可行版本 |
| ponytail 注解 | 每次走捷径打 `# ponytail: <原因>` 注释 |

### 10.2 决策阶梯

写代码前爬这个梯子，第一级成立就停：

```
1. 需要存在吗？         → YAGNI，跳过
2. 代码库里已有？       → 复用，别重写
3. 标准库能做？         → 用标准库
4. 原生平台特性？       → 用原生（如 <input type="date">）
5. 已装依赖能覆盖？     → 用已有依赖，别新增
6. 能一行解决？         → 一行搞定
7. 最后：最小可行       → The minimum that works
```

### 10.3 安全边界

- validation / error handling / security / accessibility 永不删
- 只约束实现阶段，不跳过分析
- 每次走捷径打 `# ponytail: <原因>` 注释

## 15. 深挖引擎 v2 实现说明（踩过的坑与对策）

这一节记录的是**实测得来的硬约束**，不是推测。改动这块代码前请先读它。

### 15.1 上游中转的真实限制（实测）

| 现象 | 实测结果 | 对策 |
|------|---------|------|
| 请求频率 | 连续发 3 次后被拒：`rpm exhausted` / `inference exceeds tpm/rpm limit`，要等满 60 秒 | `llm.Pacer` 匀速闸门，默认 `llm_rpm=3`，留 20% 余量（实际间隔 ≈ 24s）。**不要并发** |
| 推理吃预算 | `deepseek-v4-flash` 会把 `max_tokens` 全烧在思考上：`completion=3000 / reasoning=3000 / content=""`，接口不报错 | ① 识别该特征并自动抬高预算重试；② 见 15.2，根治办法是关掉思考 |
| 单次超时 | provider 内写死 `timeout=60`。开着思考做复杂提取时，60 秒内生成不完 | 关掉思考后单次 1-5 秒；`AIClient` 的 timeout 未改动 |
| TPM 冷却 | 连跑两轮之后会持续返回 `inference exceeds tpm/rpm limit`，**要好几分钟才恢复**（不只是 60 秒的 RPM 窗口） | 空输出且 `completion=0` 判为限流，**退避式**重试：24s → 48s → 72s → 90s（上限 90s），共 6 次机会。固定间隔重试会在 2 分钟内烧光机会然后整批观察白丢 |

**运营含义**：上游额度是和 bot 自己的对话**共享**的。
连续蒸馏会占满配额几分钟，期间机器人的回复会失败。
所以自动化必须安排在机器人空闲窗口（用户作息偏凌晨 5 点睡，建议 04:30）。

### 15.2 关掉思考，但别碰 bot 的客户端

实测 `{"thinking": {"type": "disabled"}}` 被中转接受，`reasoning_tokens` 归零。
但**不能**顺手改 bot 注入进来的那个客户端 —— 机器人聊天时可能正需要思考能力。

做法：`deep_client.py` 用同一套凭据单独造一支笔（关思考、温度 0.3、不重试），
并在 `providers.Provider` 上加了可选的 `extra_body` 字段（默认 `None`，完全不影响原有行为）。
配置项：`deep_client_direct` / `deep_disable_thinking` / `deep_extra_body` / `deep_temperature`。
造不出来时自动退回注入的客户端，宁慢不废。

### 15.3 三种"重复"必须分开算

v1 把跨源重复算成了刷屏，导致结论跑偏（"有 26 条重复发送"）。

| 类型 | 含义 | 处理 |
|------|------|------|
| 跨源重复 | 同一次发言被 chat_logs / super_memory / private_memory 各记一份 | 合并为一条，记录来源清单，**不算重复** |
| 同渠道重复 | 同一渠道里同一句话在多个时间点出现 | `repeats` 计数，**这是真实行为特征** |
| 平台噪声 | `[引用]` 前缀、链接本体 | 剥离成 `quoted` / `link` 标记位，保留为可查证据 |

### 15.4 证据链：让"编造"无处藏身

1. 每条消息一个编号（M0001…），语料投喂时直接带编号。
2. 模型每条结论必须填 `evidence`。
3. 解析时 `_norm_ids` 统一编号写法，核对是否存在：
   - 声称有证据但编号一个都不存在 → **判为编造，整条剔除**
   - 部分编号不存在 → 置信度 ×0.6 并标记 `unverified`
4. 全部结论过一遍 `verify_all_citations`（确定性，不依赖模型）。
5. 终审再让模型逐条判定 supported / weak / unsupported。
6. 人格文件里每条结论后面直接印出 `M0007「原文…」`，人可以直接翻回去核对。

### 15.5 等级不再是装饰

v1 的病根：`sections_for_level("L3")` 说要 S0-S7，但渲染器只会写 S0-S5+S9+S11，
**L3 的立身之本（时间层、环境层）根本没有代码**，所以 L3 文件 ≈ L1 文件。

v2：`sections.py` 是 12 个 section 的唯一真相，等级 → section 集合 → 实际调用与渲染，
三处对齐。`expected_entries(level)` 给脆弱度评分提供分母，`feasibility()` 明确告知
"这个等级相对现有数据量是否吃得消"，吃不消就写在文件开头的可信度声明里。

### 15.6 薄数据下的诚实

数据只有几十条时，最大的风险不是"提取不够多"，而是**提取太多**——
用常识补出一个典型的人。所以：

- 系统提示词把"允许没有""宁缺毋滥""不许编造"写成铁律
- 提示词里显式给出样本量（`digest`），让模型知道自己的证据基础有多薄
- 模式层专门产出一条「样本充分度」，直接告诉读者这份文件能信到什么程度
- 文件开头有「可信度声明」，超纲时明确写"请当作薄证据下的最大努力"

## 16. 连续蒸馏与人格账本

### 16.1 为什么必须连续

一次性的蒸馏有三个治不好的毛病：

| 毛病 | 具体表现 |
|------|---------|
| 重复烧钱 | 每次重跑都把历史语料重新喂一遍，而上游只有 3 请求/分钟 |
| 认识会丢 | 跑完就覆盖文件；上一轮建立的判断，除了在备份里躺着，对下一轮毫无影响 |
| 不会成长 | 同一句话被反复确认，文件上看不出"这条越来越硬了"；早该退场的判断也不会自然退场 |

所以：**人格文件是账本的快照，可以随时重印；账本本身只增不删（只退休）。**

### 16.2 账本存什么

`data/ledger/{target_id}.json`

```jsonc
{
  "runs": 3,                       // 连续蒸馏轮次
  "entries": {                     // 结论，按 section 分组
    "linguistics": [{
      "eid": "linguistics::高频词",  // 稳定主键 = section::label
      "label": "高频词", "value": "你好×13",
      "confidence": 0.78,
      "evidence": ["M0001", "M0031"], "counter": [],
      "state": "active",            // active | suspect | dormant | retired
      "first_seen": "…", "last_supported": "…", "last_checked": "…",
      "confirmations": 3,           // 被证据确认的次数
      "silent_runs": 0,             // 连续多少轮没被提及
      "history": [{ "at": "…", "event": "confirmed", "from": 0.72, "to": 0.78 }]
    }]
  },
  "journal": [{ "run": 3, "at": "…", "events": { "confirmed": 12, "created": 5 } }],
  "mid_of_fp": { "指纹": "M0031" },  // 消息身份 → 编号（跨轮稳定）
  "next_mid": 32,
  "quotes": { "M0001": { "q": "你好", "d": "2026-08-05", "h": 15 } }
}
```

### 16.3 状态机（最重要的一条规矩）

```
(新观察) ──> active ──被新证据确认──> active（确认 +1，置信度上升）
              │
              ├─ 连续 N 轮未被提及 ──> suspect ──> dormant
              │                      （沉默只降级）
              ├─ 被反证且反证更强 ──> retired
              └─ suspect / dormant / retired 再获证据 ──> active（复活）
```

**「沉默」不等于「错了」。** 一个人这段时间没出现，不代表他变了 ——
所以沉默只能把条目推进到存疑／沉眠，**永远不能因为它退休**。只有反证才能推翻结论。
（`ledger._apply` 里没有任何一条 silent 分支写 `RETIRED`，这是刻意留的。）

沉眠与已推翻的结论**不删除**，收进人格文件的「🪦 墓园」保留 ——
它们仍是这个人历史的一部分，只是不再参与"他怎么说话"。

### 16.4 职责分工

| 谁 | 负责 |
|----|------|
| LLM | 只回答"这波新数据说明了什么"（产出条目，带证据与反例） |
| 账本 | 只负责"这对已有结论意味着什么"（状态迁移、置信度演化、历史记账） |

这样分开之后，人格的演化过程是**确定性、可审计**的，而不是又一次黑箱生成。
置信度公式也是固定的：确认 = `old*0.7 + observed*0.3 + 0.03×新证据数`（上限 0.96，无新证据时不虚涨）。

### 16.5 三种模式

| 模式 | 何时用 | 成本 |
|------|--------|------|
| `full` | 首次蒸馏、数据量跳变、用户强制重算 | L3 约 9 次调用（约 3.5 分钟） |
| `incremental` | 账本已存在且新增不超过 300 条（默认） | L3 约 4 次调用（约 1.5 分钟） |
| 跳过 | 新增为 0 | 0 次调用，直接告知"账本已收录全部 N 条" |

增量模式下：
- LLM 只看到**新增语料**（统计基线仍用全量语料算，保证数字一直是对的）
- 提示词里带上「已有结论清单」，要求模型做增补／修正而不是重新发明
- **不做 L3 定稿**：合并、去重、冲突处理已由账本确定性地完成，让模型再做一遍纯属浪费额度

### 16.6 编号终身唯一

`evidence.normalize(messages, id_map, start)` 用「指纹 → 编号」映射复用旧编号。
同一句发言在任何一轮蒸馏里都是同一个 `M####`，所以历史上写下的引用永不失效 ——
这是增量模式能成立的前提。（否则第二轮重编号，老结论的引用会指向别的消息。）

模型看到旧结论里的 `M0007` 时，这个编号不在本轮语料里；若不做处理会被判成"编造"并扣分。
所以校验前先把**账本累积的引证表**和本轮索引合并（`ledger.known_index`）。

### 16.7 审核仍是闸门

记账放在 `approve()` 而不是蒸馏时：**账本是"人认可过的认识"**，
被丢弃的蒸馏不该污染它。蒸馏只产出 `ledger_plan`（"如果通过会发生什么"），
人点通过之后才真正落账。

审核页因此新增：
- 顶部「本轮变化」：新增 / 确认 / 改写 / 遇到反证 / 复活 / 转存疑 / 转沉眠 / 推翻
- 每条结论的状态徽章（含被确认次数、首次确立时间）与本轮变更标记
- 人格文件里同样有「🔄 本轮变化」与「🕰 演化日志」

| `group_chat_decider.group_profiles` | 群活跃时段/话题/回复密度 | 环境层 |
| `group_chat_decider.conversation_chains` | 对话链参与记录 | 关系层的互动结构 |

**同时必须识别污染源**：历史上 `nexsandglass/persona/persona.md` 是随包附带的
**Demo 示例画像**（文件里写着「仅供 Demo 参考」），内容是
「AI 记忆系统用户 / Windows / Python 3.11+」这类虚构设定。
把它当语料会把这些设定蒸馏成被蒸馏者的人格。
2026-10-19 该目录已随上游移除，该文件不存在了；`data_collector._persona_paths()`
也不再把它列为候选。**但原则仍然有效**：任何"随包附带的虚构设定"若再出现，
都必须识别并剔除，并在扫描结果里明确告知"我剔除了什么、为什么"。

「平台事实」与「发言」严格分开计数：
`stats.unique` 只算发言（否则等级判定会虚高），`stats.fact_count` 单独统计。
启发式提取只跑在发言上（否则「好感度评分 72」里的「好感度」会被当成口头禅），
但事实同样有编号、可被引用。

### 17.2 语料不再被静默截断

之前 `corpus_chars=60000` 一超就砍，多出来的语料**默默消失**，
产出里却写着"不抽样"。现在：

- 语料按 `chunk_chars` 切块，**每批 × 每块各一次调用**，一块都不少
- 多块时每批先做一次「块间合并」，再做一次全局定稿
- 分块提示词里写明"这是第 c / N 块，只就这一块下结论，不要否定其他块"

### 17.3 预算不够时明说，而不是中途静默停下

`sections.plan_calls()` 先算账，超预算按这个顺序降级，**每一步都留痕**：

```
1. 合并取证批次（几层挤一次调用）
2. 砍 L4 终检
3. 砍 L3 定稿（账本会做确定性合并）
4. 合并语料块 ← 关键：块只是切片方式，合并后语料一点不丢
5. 最后才放弃最低优先级的层，并记入账本「待补」
```

第 4 步是刻意的：**砍层会永久丢失那一层的覆盖，合并块不会**。
所以顺序上先合并块，实在不行才砍层。

产出的「🔎 覆盖与缺口」一节会写明：LLM 取了哪些层、覆盖率多少、
未覆盖的是哪些、缺哪些数据源、影响了什么。

### 17.4 断点续跑

未覆盖的层写进账本 `pending_sections`，下一轮自动排到取证队列最前面，
并在日志里提示"断点续跑：优先补 XX 层"。

### 17.5 S8 完整重建不再永远是空的

之前 S8 只在 L4 出现，而 L4 需要 5 万条消息 —— 等于**永远看不到**。
现在把它拆成两半：

| 部分 | 来源 | 何时可用 |
|------|------|---------|
| 置信度热力图 | 确定性计算 | 任何等级 |
| 薄弱区与该补什么 | 确定性计算 | 任何等级 |
| 一致性检查（矛盾检测） | 确定性计算 | 任何等级 |
| 可复现锚点 | 按置信度×确认次数排序 | 任何等级 |
| 触发 → 反应 | 从行为层结论改写 | 任何等级 |
| 条件反射库 / 微反应映射 / 梗库 | LLM | L4 |

矛盾检测是确定性的三条规则：条目自带反例、同 label 跨层不同值、
反义对（喜欢/讨厌、主动/被动…）且话题重叠。算得出来的东西不麻烦模型，
而且算出来的比让模型凭空写的更可靠。

**但「算得出来」不等于「算得对」**。第一版规则跑出四条「矛盾」，全是误报：

- 「短句为主（如你好），偶有长句」和「短句为主（平均 16 字）」被判成冲突
  —— 因为前者**自己**同时含「短句」和「长句」，而规则只检查
  "两个词分别出现在两边"，没排除自说自话。
- 「重复发送」（行为层）与「重复发送」（语言层）说的是同一件事，
  只因为措辞不同被判成「口径不一致」。

现在的判法：给每段话在反义对上算**极向分**（含否定词翻转，
「从不主动」≈「被动」），只在两边极向相反且都非零时才判冲突；
同 label 跨层则在**说法重叠度低**时才算不一致。修完的精度：

| 用例 | 期望 | 结果 |
|------|------|------|
| 短句为主，偶有长句 ⟷ 短句为主 | 不报 | 0 条 ✓ |
| 在群里很主动 ⟷ 在群里很被动，从不主动说话 | 报 | 1 条 ✓ |
| 重复发送同一句 ×2（措辞不同） | 不报 | 0 条 ✓ |

### 17.6 证据附卷

人格文件里的引证为了可读只显示 60 字截断。审核通过时会另写一份
`{目标}_{等级}.evidence.md`：按层分组，把每条结论引用到的原文**完整列出**
（引证存储长度提到 200 字），并单独列出"引用了但原文缺失"的编号清单。
要核对"这条结论到底从哪句来的"，看这一份就够，不用翻原始日志。

### 17.7 图灵测试结果留档

图灵测试是衡量"像不像"的唯一硬指标，之前测完就丢。现在结果写进账本
`ledger.turing`（状态/得分/判定方式/轮数/命中数），随人格文件一起可查。

### 17.8 易用性

**命令行入口 `cli.py`**（定时任务与自动化不再依赖点网页）：

```
cli.py sources                              看有哪些数据源
cli.py scan    --target X                   扫描数据量、源状态与缺口
cli.py distill --target X --level L2 --consent [--approve] [--watch]
cli.py ledger  --target X [--json]          看账本（结论状态/沉默轮数/演化日志）
cli.py export  --target X [--out DIR]       导出人格文件/注入卡/账本/证据附卷
cli.py turing  --target X [--rounds 5]      跑图灵盲测
cli.py forget  --target X --eid "..."       人工抹除某条结论
cli.py selftest                             内置自检（不调 LLM）
```

蒸馏必须显式给 `--consent`（对应伦理协议的知情同意）；
`--approve` 会跳过人工审核并在审计里记为 `operator=cli`。

**界面增强**：

- 新增 **人格账本** 标签页：结论状态、确认次数、沉默轮数、演化日志，
  支持按条「抹除」（人工推翻机器）
- 新建页的扫描结果升级为**代价预估**：预计几次调用、大约几分钟、
  预算不够会降级成什么样、本轮不会覆盖哪些层、缺了哪些数据源
- 进度页新增**各层进度**列表（哪一层在跑、捞到几条）
- 审核页新增：**只看本轮变更**过滤、按置信度**批量移除**、
  四种**导出**（人格文件/注入卡/证据附卷/账本 JSON）
- 新增 **⚙ 设置** 面板：限速、调用上限、分块粒度、阈值等全部可视化配置

> 过滤时保留原始下标 —— 审核页的编辑/删除都是按下标操作的，
> 直接 `filter` 会让"编辑过滤后的第 1 行"改到别的条目上去。

### 17.9 语料语义陷阱：群聊 @ 的方向

证据附卷第一次跑出来就暴露出一个**方向性错误**：结论写着
「被称呼为『示例昵称』」，可信度 0.9。但翻附卷里的原文，
那是**他自己发出的**「@示例昵称 我好无聊啊」——
群聊里 `@某人 内容` 是**发言者在称呼对方**，不是他被叫。

这种错很危险：它会把"他给别人的称呼"记成"他的名字"，一路传进人格注入卡。
修法两条：

1. 语料里显式标注：行首匹配 `@名字 ` 就渲染成 `[他@了「示例昵称」]`
2. 提示词里写死这条语义，并说明"方向弄反会直接产出错误结论"

**教训**：只要平台有特有的书写约定（@、引用、转发、图片占位），
就必须在语料层标出来。指望模型自己从上下文推对方向，是不可靠的。

### 17.10 三个"第二次才想对"的实现细节

**守卫必须跑在最终状态上，不是本轮特征上。** 名字方向守卫第一版只检查本轮
LLM 产出的特征，结果一次都没触发 —— 因为那条有问题的结论恰恰是**本轮没被重新
提到**、从账本里留下来的。改成跑在 `ledger.plan()` 的最终条目集上之后，
即使模型这轮完全没提它，确定性修正仍然生效。

**沉默的语义要抠准。** 全量重读同一份语料时，模型往往只是换了措辞，
上一轮的 label 没被重新提到就被记成"沉默"，一轮跑出 15 条转「存疑」。
正确语义是：**只有真的出现了新对话，沉默才算数**。
所以 `advance_silence = first_run or delta_messages > 0`，
其余情况只更新 `last_checked`，不推进 `silent_runs`。
阈值也放宽到 `suspect_after=3 / dormant_after=8`。

**模型会产出"占位结论"。** 证据不足时它会写 `label=角色定位, value=语料不足,
confidence=0` —— 这不是结论，只是把"不知道"写成了条目，四条一起堆在身份层
纯属噪声（热力图和薄弱区已经专门讲这件事）。现在 `_norm_entries` 直接丢弃
置信度低于 15% 的条目，`ledger.prune_weak()` 负责清历史存量。

### 17.11 零调用重印

`cli.py render --target X`（API 动作 `render`）：直接用账本里的结论重新印一份
人格文件与证据附卷，**0 次 LLM 调用**。用途有三 ——
换个等级看同一份认识、把确定性修正同步进成品、单纯重排版式。
重印时会重新收集一次语料（纯本地读取，不消耗额度）以便重跑守卫与洞察。

## 18. 落沙：一个被路径和格式同时藏起来的语料库（v2.3）

这一节记录一次典型的"以为没有数据，其实是没找到"。它值得单独写，
因为**失败的形态不是报错，而是安静地返回 0 条**。

### 18.1 位置错了

DESIGN 从 v1 起就把 `sandglass.txt` 列为核心数据源，路径**曾**写的是
`nexsandglass/sandglass.txt`（程序目录，错）。实际位置由路径解析规则定义
（2026-10-19 起由 `sandglass_lite.py` 的 `_NB` 承担，规则与上游 `sandglass_paths.py` 一致）：

```python
_NB = os.environ.get("NEXSANDBASE_HOME") or os.path.join(os.path.expanduser("~"), ".neurobase")
_SANDGLASS = os.path.join(_NB, "sandglass.txt")
```

也就是 `<用户目录>\.neurobase\sandglass.txt`（本机实测图，为 272 KB / 4080 行，
跨度约三个月）。目录里还有 `sandglass.db`、`shadow_sand.db`、
`decision_particles.txt`、`emotion_vocab.json`。

同理 `persona.md` 的真实位置也在 `~/.neurobase/persona/`（该目录是空的），
程序目录里那份只是随包示例 —— 所以"排除示例文件"的判断是对的，
但"把 persona.md 当数据源"这条设计从两头都不成立。

### 18.2 格式有三代，且发送者不在 sender 字段里

```
2026-06-18 00:08:58 | user | 你好                              ← 裸行，无发送者
2026-06-24 15:38:10 | user | [群20001] 10003: 小a是傻子吗      ← 老格式，uid 在正文
2026-06-28 17:50:00 | user | [群:20001] [示例用户(10003)] 你好呀   ← 新格式，昵称+uid
```

三个坑叠在一起：

1. **`sender` 字段只有 `user` / `agent`**，真正的发送者在正文里。
   按 `sender == 目标 id` 匹配，永远匹配不上 → 安静返回 0 条。
2. **正文可以跨行**（机器人回复常带换行），必须状态机逐行读，
   不能 `splitlines` 当一条一条。
3. **正文里还有引用标记**：`[引用:昵称(uid)] …`、`[当前] …`、`[合并转发消息]`。

### 18.3 两次差点污染（比路径问题更危险）

**第一次：开发期测试数据。**
落沙 2026-06-24 01:41~01:47 那六分钟里有一批当年调试人格用的假数据：
`我叫张三，是一个程序员`、`我的生日是3月15号`、`hello world, this is a test`、
`周末喜欢宅在家里打游戏`。
倒进去会把「张三 / 程序员 / 3月15号生日」蒸馏成被蒸馏者本人。
→ 加了 `_SG_FIXTURES` 特征表，剔除 27 条。

**第二次：一个群里十几个人的话。**
我第一版把"没有发送者标记的行"一律当成目标说的 —— 结果 972 条里
**混进 421 条别人的发言**（日升、占位昵称、南风知我意、占位群友A…）。
这些人的口头禅、情绪、话题会被算到他头上。
→ 改成 **两遍扫描**：先从 `昵称(uid)` 学出「昵称 → uid」映射，
再据此逐条判定归属；判定不了的（38 条）**宁可不收**。

### 18.4 顺带证实名字方向守卫

落沙里有 `[示例用户(10003)]` —— **目标的昵称是 `示例用户`**。
而早先那条转发里 `转发: 示例用户: …` 与 `示例昵称 : …` 并列，
说明 `示例昵称` 确实是**别人**。§17.9 里守卫把它从 90% 降到 45%，
判断正确。现在还会产出「昵称对应」事实：`示例用户` ↔ 10003。

### 18.5 收益

| | 修之前 | 修之后 |
|---|---|---|
| 独立发言（去重后） | 36 条 | **291 条**（原始记录 668 条） |
| 时间跨度 | 11 天 | **2.6 个月**（06-18 ~ 09-05） |
| 群聊语料 | 0 | 243 条 |
| 带机器人回复的上下文 | 16 条 | 198 条 |
| 平台事实 | 15 条 | 28 条（新增决策粒子 15、昵称对应 1） |
| 建议等级 | L0（超纲） | L1（名实相符） |

最直接的改善是 **S6 时间层**：它之前一直是"没有任何活跃结论"，
现在有 2.6 个月的跨度可以建立节律。

### 18.6 顺带修掉的两个统计口径问题

**"原始条数"不等于"语料量"。** 668 条原始记录去重后只有 291 条独立发言
（落沙里同一个短句会重复几十次）。只报原始条数会让人高估语料量，
等级判定也会虚高。现在 `scan` 同时给出两个数。

**统计刷新不该改写模型结论。** 有一次用 L1 跑（L1 不在 `deep_levels` 里，
LLM 根本没参与），结果统计基线把 LLM 得出的结论"改写"掉了 11 条 ——
拿粗尺子量细活。现在 `ledger.plan(stats_only=True)`：
LLM 未参与时，统计来源的条目只能动自己人，绝不覆盖模型结论。

### 18.7 数据根为什么在 `~/.neurobase`（以及要不要搬）

`~/.neurobase` 不是随手写的，是**有意为之**：

- 历史上 `nexsandglass/sandglass_mcp.py` 是一个 **MCP Server**（「任何 MCP 兼容 Agent
  可直接调用」），NeuroBase 本身是**独立系统**（自有版本号、自有 vault 概念），
  不是 EggBloom 的从属模块。**2026-10-19 起该目录已移除**，MCP Server 不再随包分发
  （需要的话从上游仓库自行获取）；但"数据放用户级目录"这个决定**依然成立**。
- 放在用户级目录有三个实际好处：换掉整个 app 目录（升级/重装）不会丢记忆；
  多个前端（Electron 界面 / MCP 客户端 / 别的 Agent）共享同一份记忆；
  备份就是拷一个目录。
- 体积 **1.4 MB**，跟"C 盘紧张"无关。

**但这里确实有该调整的地方**：`PORTABLE_STRUCTURE.md` 承诺
「整个文件夹复制到任意路径、任意电脑直接运行」，而 NeuroBase 的记忆
不在文件夹里 —— 照文档复制走，沙漏、影子灵魂、决策粒子会**静默全部丢失**。
文档里一个字没提。这个矛盾是真问题，而且属于文档责任，不是代码 bug。

**要不要搬？** 搬的代价与收益：

| 方案 | 代价 | 收益 |
|------|------|------|
| 不动（推荐） | 无 | 保持与 NeuroBase 独立系统的设计一致 |
| 设 `NEXSANDBASE_HOME` 环境变量 | 要保证 Electron 与 bot 子进程都能继承到 | 零代码改动即可换位置 |
| 改 `sandglass_paths._NB` 优先用程序目录旁的 `.neurobase` | 动机器人**正在用的活记忆**，需停机 + 迁移 + 校验（约 25 个模块 `from sandglass_paths import _NB`，改一个文件即可让它们全部跟随） | 真正兑现"可移植"承诺 |

**插件这边的处理**（已实现，纯增量、无风险）：不再自己重算路径，而是
**优先问程序的 `sandglass_paths._NB`**，其次 `NEXSANDBASE_HOME`、
插件配置 `neurobase_home`、程序目录旁的 `.neurobase`、最后 `~/.neurobase`；
`scan` 会把"实际用了哪个数据根"写进源状态。这样无论将来怎么调整，插件都跟着走。
扫描多个候选也是有意的 —— 万一搬了家而配置没跟上，至少不会安静地报 0 条。

## 19. 科学测量层与分层存储（v2.4）

用户的批评：**"已经滑向科幻/虚构了，应该落到心理学、精神病学、社会学上；
我们是为了人格文件服务——高精度人格可能到 1GB，那时候使用就更需要
结构上的优化。"** 两点都对。

### 19.1 内容模型的修正：从"结论清单"到"可执行规范"

之前蒸馏出来的是一叠结论（"短句为主""爱用语气词"）。要让另一个模型
照着说话，**结论没用，参数和例句才有用**。所以新增 `style_profile.py`：

| 量化项 | 例（实测 10003） |
|--------|----------------------|
| 句长 | 平均 17.2 / 中位 **9** / P90 27 / 最长 270 |
| 标点 | 句号 3.4%、**问号 14%**、感叹 0.7%、**无标点 47%** |
| 口头禅 | 「啊」×26、「吧」×13、「嘛」×9（平均每条 0.27 个） |
| 连发 | 一口气平均 2.39 条、最多 20 条，45% 场合连发 |
| 语域 | **私聊平均 12.1 字 vs 群聊 19.9 字**（偏移指数 0.39） |
| 漂移 | 6 月平均 20.9 字 → 7 月 **9.5 字** → 8 月 14.7 字 |
| 例句 | 12 条真实原话当风格锚点（覆盖短句/长句/问句/深夜/群聊） |

注入卡同步升级为三层：**可执行参数 → 真实例句 → 结论条目**。
模型照数字做事，比照"简洁"这种形容词可靠得多。

### 19.2 科学测量层（`psych.py`）与那条不能碰的线

三条铁律写在模块最前面：

1. **代理指标，不是心理测量。** 大五的每个分数都来自可观察的语言行为
   （连发倾向、问句率、负面词密度），不是量表。置信度上限 0.6，
   且每条必须附「观察基础」和「反例」。
2. **只记录可观察行为，绝不做临床判断。** "深夜 0-6 点发言占 33%" 是数据；
   "有抑郁倾向" 是诊断。前者可做，后者永远不做。
3. **给不出证据编号的测量不成立。**

实测输出（每条都带反例）：

| 维度 | 方向 | 观察基础 | 反例 / 限制 |
|------|------|----------|-------------|
| 开放性 | 偏低 | 话题熵 0.848，提问率 14% | 话题集中在游戏与技术，未必是探索新领域 |
| 外向性 | 中性 | 语气词 0.27/条，连发 45% | — |
| 宜人性 | 直接/带攻击性表达多 | 礼貌 1% vs 攻击/调侃 4% | 群内"骂人"常是亲昵玩笑 |
| 尽责性 | 作息分散 | 时段标准差 7.3h，深夜占 33% | 更可能反映放假/夜猫子习惯 |
| 情绪稳定性 | 偏平稳 | 负面词 2%，正面/玩梗 7% | 「无聊」「烦」是高频口头禅 |

外加：社会语言学（TTR 0.556、言语行为分布、话语标记、**语域偏移指数**）、
社会学（角色集：学生/玩家/技术使用者/群成员；群体语言采纳率 0.38）。

**框架来源是方法论，不是诊断标准**——大五只取"行为↔维度"的对应关系做代理，
社会语言学用语域/言语行为理论，社会学用角色集与群体语言。

### 19.3 分层存储（`persona_store.py`）：为 1GB 做的结构优化

之前一个对象所有东西塞在两个文件里。到 1GB，**想看"他怎么称呼对方"
就得把整个文件读进内存**。现在拆成四层，每层独立寻址：

```
data/personas/{target_id}/
├── manifest.json          索引：各层文件/字节数/条目数/证据分片区间
├── card.md                热层 ≤5KB，常驻（注入卡，直接喂模型）
├── persona.md             温层（人看的）
├── evidence.md            证据附卷
├── sections/{key}.json    冷层：每层一个文件，O(1) 定位
├── measures/*.json        风格画像 + 科学测量
└── evidence/e####-####.json  底层：原文引证按编号分片（每片 1000 个编号）
```

关键 API：`load_section(key)` 只读一层；`load_evidence(mids)` **只加载需要的分片**。
有了 manifest，"取他称呼对方的所有证据" = 查索引 → 读那一片 → 完事，与总体积无关。

实测（10003，尚在早期）：manifest 236KB，card 4.7KB 常驻，
7 个 section 独立寻址，1 个证据分片，按需取证只读命中的那一片。

### 19.4 顺带修掉的三个 bug

1. **`normalize` 丢上下文字段**：`scope`（私聊/群聊）、`context`（机器人当时的回复）
   在 `prepared` 里就没有，合并时也没补 —— 291 条的 scope 全是 None，
   机器人的真实回复一条没带上。修掉之后：场景对比、语域偏移、
   **162 条图灵成对样本**全部可用。
2. **标点正则写错**：`"？?"` 里的 `?` 被当成量词（"？可有可无"）→ 问号率恒等于 100%，
   一条看似合理的假结论。改成字符类 `[？?]` 后：问号 14%、无标点 47%。
3. **静默吞异常**：render 里风格计算失败被 `except: style=None` 吃掉，
   排查花了 20 分钟。现在失败会打到 stderr 并留下 traceback。
   **教训：凡是 `except: pass` 能写成"带日志的降级"，就不要静默。**
